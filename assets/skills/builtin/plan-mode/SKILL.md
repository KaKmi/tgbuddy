# 计划模式

计划模式是 TgBuddy 的显式工作流：**先规划、后执行**。进入由用户通过输入框上方的
权限模式 chip 切换到「计划模式」（对应 Codex 的显式模态）；本技能负责教会模型在
这个模式下如何正确调研、写计划、提交审批，以及审批后的行为。

## 什么时候应该用计划模式

- 任务复杂，涉及多个文件或模块的联动修改；
- 影响面大或不可逆：删除、移动、安装/升级依赖、修改配置、批量改写；
- 用户意图不明确，需要先确认方案再动手；
- 用户已经手动切到「计划模式」——此时必须按本流程工作。

## 模式下的硬性规则（系统强制，不要尝试绕过）

计划模式下权限系统只放行以下调用，其余一律拒绝：

1. **只读工具**：`read`、`glob`、`grep`、`web_search`、`skill`；
2. **只读命令**：`ls`、`cat`、`head`/`tail`、`git status|log|diff|show|branch`、
   `rg`、`find`（不带 `-delete`/`-exec`）等，由系统按命令内容判定；
3. **只读 MCP 方法**：方法名以 `get` / `list` / `search` / `read` / `fetch` /
   `query` 开头（如 `postgres-read.query`），用于调研外部数据；
4. **唯一允许的写入**：`write` / `edit` 且目标路径以 `.md` 结尾——用于产出计划
   文档本身。

不要尝试用奇怪的方式绕过只读限制（例如用 bash 拼字符串写文件、调用写类 MCP 改
数据）。被拒绝时系统会返回原因，按提示调整即可，把需要执行的写操作记进计划，
等批准后再做。

## 调研阶段（规划前）

1. **先读上下文**：用 `read` 读取任务相关的关键文件（入口、配置、测试、现有实现），
   用 `glob` 找到相关文件的分布；
2. **确认现状**：用只读命令核对依赖版本、git 状态、构建/测试命令的实际行为，
   避免计划建立在错误假设上；
3. **识别写点**：调研中发现的每个写操作（改哪个文件、跑什么命令、删除什么），
   逐条记入计划的「将执行的写操作/命令」清单，**不要当场执行**；
4. **范围收敛**：明确哪些文件在范围内、哪些明确不动（不熟悉的第三方代码、
   与任务无关的模块），避免计划失控。

## 计划结构（markdown，直接提交给用户审批）

计划必须是一份可执行的完整 markdown，包含以下部分：

```markdown
# <任务名>

## TL;DR
2-3 句话讲清要做什么、改动范围、关键风险。

## 目标
这次要达成的结果，写可验证的行为（如「xxx 用例通过」）。

## 范围与排除
- 范围内：……
- 明确不动：……

## 实施步骤
每一步一句话，具体到文件与命令：
1. 修改 `src/xxx.ts`：把 `yyy` 改成 `zzz`（原因）。
2. 新增 `tests/xxx.test.ts`：覆盖场景 A/B。
3. 运行 `bun test tests/xxx.test.ts` 验证。

## 将执行的写操作/命令清单
逐条列出批准后要做的写入与命令（这是用户审批时的重点）：
- write `src/xxx.ts`
- bash `bun install <pkg>`
- delete `tmp/cache/**`

## 验证
用什么命令/用例证明任务完成（测试、构建、手工核对步骤）。

## 风险与回滚
主要风险（如破坏性命令、配置变更）与失败时的回滚方式。
```

计划**必须具体到文件路径和命令**，不能只写「优化一下性能」这种含糊目标。

## 提交与审批

1. 调研完成、计划写好之后，调用 **`exit_plan_mode`** 工具，参数 `plan` 传入完整
   markdown 计划；
2. 工具会挂起等待用户审批：
   - **批准**：自动退出计划模式，按计划逐步执行；
   - **拒绝**：不会退出计划模式，系统会把用户的意见带回。把意见吸收进计划，
     **修改后重新提交**，绝对不要在被拒绝后直接执行。

## 常见错误

- 计划写得太粗：没有具体文件、命令、验证方式；
- 调研不充分就提交：对现状的判断建立在猜测上；
- 被拒绝后直接执行：违反模式规则，写操作会被系统拒绝；
- 在计划模式下尝试写非 `.md` 文件：会被拒绝，把写入需求记入计划清单。
