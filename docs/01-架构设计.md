# TgBuddy 架构设计

> 一个精简版的 Agent 桌面应用：Electron + React + **pi 内核**。
> 目标是学习架构，所以每一层都保持可读、可替换，不追求功能完备。

---

## 0. 一句话定位

面向用户的四个概念，正好对应本文的四个设计章节：

| 用户看到的 | 实际是什么 | 章节 |
|---|---|---|
| **模式** | 权限模式（plan / auto / bypass） | 4.4 |
| **专家** | systemPrompt 或独立子 Agent；多个专家可组成团队 | 5 |
| **技能** | Agent Skills 标准的 `SKILL.md` | 4.5 |
| **连接器** | MCP Server | 4.6 |


**只做 Agent 模式**（不做 Chat 模式），使用 `@earendil-works/pi-agent-core` + `@earendil-works/pi-ai`，宿主负责**存储、权限交互、事件传输、并发控制**，并额外提供**多 Agent 编排**。

规模目标：`src/` 下 30–40 个文件，优先保持单包结构和清晰边界。

## 1. 内核选型：为什么是「库」而不是「子进程」

pi 提供两种集成方式，这是第一个要拍板的决定。

| | (a) 直接 import `pi-agent-core` | (b) spawn `pi` CLI 走 RPC |
|---|---|---|
| 工具执行前弹 UI 确认 | `beforeToolCall` 钩子，**直接 await 你的 IPC 往返** | 必须写一个 pi extension（`.ts`，由 jiti 加载进**子进程**），只能用协议内置的 4 种 dialog |
| 拿到的数据 | 同进程对象：完整 `assistantMessage`、已校验的 `args`、`AgentContext` | 序列化后穿过 stdout 的 `{toolName, args}` |
| 自定义 UI | 任意（diff 预览、参数编辑器、文件树都行） | `select` / `confirm` / `input` / `editor` 四选一 |
| 授权状态 | 主进程内存里，秒查 | 跑在子进程 extension 里，跟主进程隔离 |
| 多 Agent | `new Agent()` × N，几乎零开销 | 每个 agent 一个 Node 进程（~80–150MB） |
| 打包 | 纯 ESM、无 native、可直接进 esbuild 产物 | 需要装 `pi-coding-agent`（带 photon WASM + jiti + cross-spawn） |

**结论：选 (a)。** 我们的核心需求就是深度定制的权限确认 UI 和多 Agent 编排，(b) 会把这两件事都变成二等公民。

pi 官方文档 `docs/rpc.md:5` 自己也这么建议：Node.js 应用应该直接用库，不要 spawn 子进程。RPC 模式是给跨语言客户端准备的。

### 依赖边界

```
✅ @earendil-works/pi-ai@^0.82         纯 ESM，无 native，provider SDK 是 lazy import
✅ @earendil-works/pi-agent-core@^0.82  纯 ESM，agent.ts / agent-loop.ts 零 node: 导入
❌ @earendil-works/pi-coding-agent      依赖 photon WASM + jiti + cross-spawn，不适合 bundle
```

**不要引入 `pi-coding-agent`。** 它的内置工具（read/write/edit/bash/grep）我们自己实现——反正也需要加路径沙箱。但它的两份文档要精读，是我们抄设计的来源：`docs/session-format.md` 和 `docs/compaction.md`。

`pi-agent-core` 顶层导出的压缩纯函数（`shouldCompact` / `prepareCompaction` / `compact` / `findCutPoint` / `estimateContextTokens`）可以脱离 harness 单独用，这是白送的。

## 2. 心智模型：pi 和 Claude Agent SDK 的根本差异

一句话：**Claude Agent SDK 是一个「产品」，pi 是一个「循环」。**

| | Claude Agent SDK | pi |
|---|---|---|
| **谁拥有会话状态** | SDK。你通过 `sessionId` + `resume` 跟它交互，历史的规范表示在它那边 | **你**。`agent.state.messages` 就是一个纯 JSON 数组，随便读写 |
| **谁负责工具执行** | SDK 调度 + 执行，内置工具集、内置权限系统、内置 MCP | pi 只调度，**执行 100% 是你的函数**。零内置权限、零 MCP、零 subagent |
| **谁负责持久化** | SDK。格式和位置都是它的 | **你**。或者用 `harness/session/*` 的 `SessionStorage` 接口塞自己的后端 |

这个差异直接决定了工作量的分布。

**你不用写的**（pi 最大的价值）：36 家 provider 的目录和协议差异、流式解析、partial JSON 工具参数累积、跨 provider 消息转换、token/cost 计算、OAuth 刷新、agent 循环本身、压缩算法。

**你必须自己写的**：
1. 权限授权 UI（`beforeToolCall` 里）
2. **循环上限**——pi 的 agent loop 是个裸的 `while(true)`，**没有 max turns**
3. 持久化
4. 工具集
5. 压缩的触发时机（算法给你了，什么时候调是你的事）
6. MCP（如果要）
7. 多 Agent 编排

第 2 条是最容易被忽略的坑。Claude Agent SDK 帮你想过"什么时候停"，pi 没有。多 Agent 场景下没有全局预算会直接失控。

## 3. 分层架构

```
┌─ renderer (React + Jotai) ────────────────────────────┐
│  AgentView / ToolActivity / PermissionBanner          │
│  atoms: 按 sessionId 隔离的 Map<string, StreamState>  │
└───────────────────▲───────────────────────────────────┘
                    │ IPC: AgentStreamPayload (双通道)
┌───────────────────┴─ main ────────────────────────────┐
│  orchestrator   会话编排、并发守卫、事件路由            │
│  ├── permission-service   Map<reqId, resolve> 挂起     │
│  ├── session-store        JSONL 树 + 原子写索引        │
│  ├── memory-service       记忆工具（本地文件）          │
│  ├── tools/               自己实现的工具集              │
│  └── multi-agent/         子 Agent 编排                │
├───────────────────────────────────────────────────────┤
│  kernel/  ← 唯一接触 pi 的地方                          │
│  ├── models.ts       createModels + 渠道配置           │
│  ├── agent-factory.ts new Agent(...)                  │
│  └── normalize.ts    pi 事件 → 我们自己的消息格式        │
└───────────────────────────────────────────────────────┘
```

**边界规则：pi 的「调用」只在 `kernel/`，但 pi 的「类型」允许出现在 `shared/`。**

这条比最初的版本放宽了。记录一下推理，因为这是本项目最接近过度设计的一次。

#### 曾经设计过归一化翻译层，写完砍掉了

**最初的理由**是担心内核类型从 shared 一路渗透到 renderer，导致 Provider 抽象失效，也让历史数据被特定 SDK 格式锁死。

**但这个类比不成立**，三条：

1. **pi 的消息格式本身已经是中立格式**——不是 OpenAI/Anthropic 原生格式，各 provider 在 pi 内部做双向转换。再归一化一次是重复劳动
2. **实测 pi 的类型很稳定**：0.79 → 0.82 三个 minor 里，`Message` / `ContentBlock` / `AgentEvent` / `AgentState` / `AgentTool` **一个字段都没改**，破坏性变更全在 API 表面（`streamFn` 从可选变必填）和 harness 层
3. 本项目不换内核

**翻译层的真实代价**是往返必须无损——signature 类字段（Anthropic thinking signature、Google thought signature）丢了会导致续接失败，而这个方向的 bug 症状极隐蔽（静默丢信息，几轮之后才发现续不上）。收益撑不住这个代价。

#### 改成信封模式

不翻译，但套一层信封，补 pi 不提供的三样东西：

```ts
type SessionMessage =
  | { kind: 'kernel'; id: string; createdAt: number; message: PiMessage }
  | { kind: 'notice'; id: string; notice: '...'; text: string; display: boolean }
```

| 补什么 | 为什么 pi 给不了 |
|---|---|
| `id` | 会话树的 `id` / `parentId` 需要，pi 的 Message 只有 timestamp |
| 系统通知消息 | 切换专家、压缩边界，pi 核心层没有对应类型 |
| `ToolDetails` 约定 | 结果区要消费，pi 的 `details` 是 `any` |

**版本护栏**：会话文件头记 `kernel: 'pi@0.82'`。将来 pi 真改了消息结构时，迁移脚本靠这个字段判断在读什么格式。这是不做翻译换来的责任，别省。

#### 但事件仍然要收敛

「消息不翻译」和「事件要收敛」是**两个不同的理由**，别混为一谈：

- **消息不翻译** —— 因为它落盘，往返无损的风险大于收益
- **事件要收敛** —— 因为它瞬时、不落盘，单向转换零风险，收益却很实在：pi 有 10 个事件而 UI 只关心 6 个；`message_update` 里还套了一层 `assistantMessageEvent`，摊平后 UI 少写一堆分支

所以 `kernel/normalize.ts` 保留，但只剩事件那一半。

## 4. 三个关键工程设计

### 4.1 对话保存：线性追加 + 原子写

> **⚠️ 已修订**：原设计用 pi 的 `id`/`parentId` 会话树。
> 交互设计明确回答「不需要分支 / 时间旅行」，**改为线性 append-only 日志**。
> 决策与理由见 [06-设计决策.md](06-设计决策.md) 决定 5。


存储分成两层：

- **轻量索引**走全量重写的小 JSON（`sessions.json`）——让"列出 200 个会话"不用读 200 个大文件
- **重内容**走逐行追加的 JSONL（`sessions/{id}.jsonl`）

索引文件使用原子写：

```ts
// 写：先 copy 出 .bak → 写 .tmp → rename 覆盖（rename 是原子的）
export function writeJsonFileAtomic(filePath, data): void

// 读：主文件 → 残留 .tmp（说明上次 rename 前崩溃）→ .bak，三级回退
export function readJsonFileSafe<T>(filePath): T | null
```

**JSONL 内容是线性追加，不建树。** 每条 entry 只有 `id` 和时间戳，没有 `parentId`：

```ts
interface SessionEntryBase {
  type: string
  id: string          // 8-char hex
  timestamp: string   // ISO
}
```

「回到那一步」的两个需求用更便宜的方式满足，都不需要树：

| 用户动作 | 实现 |
|---|---|
| **编辑并重发** | 截断该消息之后的所有条目——**软删除**（打 `truncatedAt` 标记，可撤销），不物理删除 |
| **以此为起点新建会话** | 复制上下文摘要进新会话，两个会话之间只记一个 `originRef` 指针，**扁平引用不成树** |

```ts
interface SessionMeta {
  // …
  /** 从别的会话派生而来，扁平引用 */
  originRef?: { sessionId: string; messageId: string }
}
```

> **为什么放弃树**：树的成本几乎全在 UI 和心智模型上——一旦有分支就要有分支切换器、diff、合并语义，而用户真正用到的只有「回到那一步」。Agent 任务是目标导向的，用户要的是「重来一次」而不是「保留两条路对比」。

**pi 的 entry 类型里有一个设计要重点抄**：`custom` vs `custom_message` 的区分。

- `custom` —— 应用状态，**不进 LLM context**
- `custom_message` —— 扩展注入的消息，**进 LLM context**，带 `display: boolean`

这正好解决 "UI 元数据 vs LLM 上下文" 的分离，避免在内核消息上挂应用私有字段。

我们的 entry 类型（先做这些，其它按需加）：

```ts
type SessionEntry =
  | { type: 'session'; version: 1; kernel: 'pi@0.82'; cwd: string }   // 首行 header
  | { type: 'message'; message: SessionMessage }
  | { type: 'model_change'; provider: string; modelId: string }
  | { type: 'compaction'; summary: string; firstKeptEntryId: string; tokensBefore: number }
  | { type: 'custom'; key: string; value: unknown }      // 不进 context
  | { type: 'truncate'; fromId: string }                 // 「编辑并重发」的软删除标记
```

「系统通知」（切换专家、模式变更）走 `SessionMessage` 里的 `notice` 信封，不单列 entry 类型——它本来就要进 LLM 上下文，当消息处理最自然。

**落盘前必须 sanitize。** 单条超过 256K chars 就截断超长 text block、截断超大 tool_result、**剥离 base64 图片**换成 `{ _truncated: true, _originalLength }`。不做这个，一个会话的 JSONL 几天就能涨到几百 MB。

> ⚠️ 读取 JSONL 必须逐行 try/catch，坏行跳过并记日志，不能让单行损坏清空整个会话。

### 4.2 多轮对话：从「外包」变成「自己管」

**这是换内核后变化最大的一块。**

SDK 托管会话的方案通常只保存一个 sessionId，再在下一轮 resume；pi 不托管会话，历史消息由宿主直接维护。

pi 里没有这回事，多轮就是**你把消息数组交回去**：

```ts
const agent = new Agent({
  initialState: { systemPrompt, model, tools, messages: loadFromDisk(sessionId) },
  streamFn: models.streamSimple.bind(models),
})
await agent.continue()   // 要求最后一条是 user 或 toolResult
```

更简单也更透明，代价是**上下文窗口管理变成你的责任**。

好消息是 pi 把压缩拆成了可直接 import 的纯函数，不用从零写：

```ts
import { shouldCompact, prepareCompaction, compact } from '@earendil-works/pi-agent-core'
```

策略照抄 `docs/compaction.md`：

- **触发**：`contextTokens > contextWindow - reserveTokens`，reserve 默认 16384
- **切点**：从最新往回累加 token 直到攒够 `keepRecentTokens`（默认 20000）
- **切点规则**：合法切点 = user / assistant 消息。**绝不在 toolResult 处切**——它必须和自己的 toolCall 待在一起
- **产物**：一条 `compaction` entry，存 `{ summary, firstKeptEntryId, tokensBefore }`
- **重建**：从 leaf 往 root 走，遇到 compaction entry 就用 summary + `firstKeptEntryId` 之后的消息

**长上下文不要直接拼进 prompt，而是把文件路径告诉 Agent 让它自己 Read**。这能降低 prompt 体积，也适合恢复和跨会话引用。

### 4.3 记忆：做成工具，不做成提示词注入

记忆采用清晰的工具边界：

- `memory-service.ts` 只有 56 行，**纯粹是配置读写**
- 真正的存取是两个工具：`recall_memory` / `add_memory`
- **代码零启发式提取**，写不写、什么时候写完全由模型自己判断
- 提示词里只给判断标准，且只在记忆开启时才注入这一 section

唯一的依赖是"内核要支持自定义工具"——pi 满足，`AgentTool` 就是个普通对象。

记忆使用本地文件存储，符合本地优先原则：

```
~/.tgbuddy/memory/
├── index.json           # { id, summary, tags, createdAt }[]
└── entries/{id}.md      # 正文
```

召回先用最朴素的方案：标题/标签关键词匹配 + 最近 N 条。**不要一上来就上向量库**，等真的不够用了再说。

#### 记忆的三层结构 —— 我们已经有了，只是没当成一个整体设计

参考某生产级 Agent 系统的记忆分层，对照下来我们其实已经有对应的三层：

| 层 | 他们的实现 | 我们的对应物 | 硬上限 |
|---|---|---|---|
| **L1 工作记忆** | Redis，最近 30 条，TTL 24h | JSONL 尾部**未被压缩**的消息 | `keepRecentTokens`（20K） |
| **L2 压缩摘要** | PG.summary | `compaction` entry 的 summary | **需补：摘要字符上限** |
| **L3 长期事实** | `search_facts` top 20，5 类 | 记忆条目 | **需补：召回条数上限** |

把三者当成一个连续体，带来两条原设计漏掉的东西：

**① 每一层都必须有硬上限。** 压缩那层我们有 `keepRecentTokens`，但**记忆召回完全没设上限**——这是个真漏洞。记忆条目攒多了会无声地吃掉上下文，而且因为它注入在最前面，挤掉的是最近的对话。

```ts
const MEMORY_RECALL_LIMIT = 20        // 单次召回条数上限
const MEMORY_ENTRY_MAX_CHARS = 500    // 单条记忆长度上限
const COMPACTION_SUMMARY_MAX_CHARS = 16_000
```

**② 层与层之间应该有晋升路径。** 压缩摘要里**反复出现**的事实，应该被提升为长期记忆——它在多轮压缩中都活下来了，说明是稳定的、跨会话有效的信息。

压缩时把生成的 summary 也交给记忆工具判断一次，让模型决定其中哪些值得长期记住。

**③ 记忆条目要分类。** 参考他们的 5 类，我们至少分这几种：

```ts
type MemoryKind =
  | 'profile'      // 用户是谁：角色、技术栈、偏好的工作方式
  | 'preference'   // 明确表达过的偏好：不要写注释、用中文、别自动提交
  | 'project'      // 项目事实：这个仓库用 bun、部署在哪
  | 'history'      // 一起经历过的事：上次那个 bug 的成因
```

分类的价值在召回：不同场景取不同类。新会话开场取 `profile` + `preference`，进入某个项目目录时取该项目的 `project`。比无差别地按关键词捞一堆精准得多。

提示词必须明确两条边界：

- **"记忆工具是工具，不是文件操作！绝对不要把记忆写入 MEMORY.md"**
- 定位为"我们一起经历过的事"而不是"关于用户的信息条目"，要求"像老搭档一样自然带入，而不是像在查档案"
- 写入标准：记结论和经历，不记流水账；不记 typo 修复、临时调试

### 4.4 权限模式与计划模式

pi **没有权限模式这个概念**，`docs/usage.md:306` 明确把 plan mode 和权限弹窗一起列为 non-goal。

计划模式完全由宿主实现：两个工具负责进入和提交计划，`beforeToolCall` 负责限制可执行操作。

三种模式，全部在 `beforeToolCall` 里分派：

```ts
type PermissionMode = 'plan' | 'auto' | 'bypass'
```

| 模式 | 语义 |
|---|---|
| `plan` | 只读调研 + 写计划文档，任何写操作一律拒绝 |
| `auto` | 白名单/只读工具放行，其余弹 UI 等用户确认 |
| `bypass` | 全部放行（危险，仅用于受信任的工作区） |

**plan 模式的判定规则**：

1. 命中只读工具白名单 → 放行（`read` / `glob` / `grep` / `web_search` / `web_fetch`）
2. `write` / `edit` 且目标是 **`.md` 文件** → 放行（计划文档一定是 markdown）
3. `bash` → 走只读命令正则判定，只读放行，写操作拒绝
4. MCP 工具（`mcp__` 前缀）→ 放行（调研用）
5. 其余一律拒绝，reason 统一为「计划模式下不允许执行写操作，请在计划审批通过后再执行」

第 3 条的只读命令判定使用白名单匹配 `find` / `grep` / `cat` / `ls` 等命令，同时要**排除 `node` / `python` / `ruby` 这些能执行任意代码的解释器**——不然 `python -c "os.remove(...)"` 就绕过去了。

**两个工具自己定义**（pi 的工具就是普通对象，各 30 行）：

```ts
// enter_plan_mode —— 模型主动进入计划模式
// exit_plan_mode  —— 提交计划请求用户审批，execute 里挂起等 UI 响应
```

`exit_plan_mode` 的审批**直接复用 6.2 那套 `Map<requestId, resolve>`**。permission / askUser / exitPlan 都抽成泛型的 `PendingRequestService<TReq, TRes>`，避免重复实现。

**提示词按模式二选一**：plan 模式下注入「## 计划模式」section（讲清楚现在只能调研和写计划、计划文档往哪写、写完要调 `exit_plan_mode`），非 plan 模式则不注入。这属于 4.4 提到的静态提示词部分。

> ⚠️ plan 模式是**会话级状态**，但模型也可以中途调 `enter_plan_mode` 切进去。所以模式变更要发事件给 UI，并带 `source: 'user' | 'tool'` 区分来源，否则界面指示器会和实际状态不一致。

### 4.5 Skills

pi 实现的是 [Agent Skills 标准](https://agentskills.io/specification)。`pi-agent-core` 直接导出了三个函数：

```ts
loadSkills(env, dirs)                  // 扫目录 → Skill[]
formatSkillsForSystemPrompt(skills)    // → <available_skills> XML 块
formatSkillInvocation(skill, args?)    // → 显式调用 /skill:name 时的 prompt
```

**坏消息**：`loadSkills` 在 **Windows 上是坏的**（已在 0.82.1 上实测确认）。

它内部的 `relativeEnvPath()` 硬编码了 POSIX `/` 分隔符：

```js
return normalizedPath.startsWith(`${normalizedRoot}/`)
  ? normalizedPath.slice(normalizedRoot.length + 1)
  : normalizedPath.replace(/^\/+/, "")   // ← Windows 走这条，返回的还是绝对路径
```

而 `NodeExecutionEnv` 在 Windows 上返回的是 `\` 分隔的路径，于是相对化失败，绝对路径被喂给 `ignore` 库，直接抛 `RangeError: path should be a path.relative()'d string`。传正斜杠的 rootDir 也绕不过去——`entry.path` 始终是反斜杠。

**所以自己写 loader**，大约 60 行，并采用以下目录约定：

```
~/.tgbuddy/workspaces/{slug}/
├── skills/{skill-slug}/SKILL.md          # 启用中
└── skills-inactive/{skill-slug}/         # 已停用
```

- **启停用通过目录搬家实现**，不额外增加状态字段
- **frontmatter 手写解析**，别引 YAML 库。支持单行值、`|` / `>` block scalar、多行缩进，只认白名单 key：`name` / `description` / `version`（`group` / `icon` 按需加）
- **`version` 是硬契约**：内置 skill 靠 semver 比较决定要不要同步到老工作区。version 不变 = 老用户拿不到新内容；不要无条件复制全部技能文件阻塞启动

**pi 的两个格式化函数照常用**——它们只读 `name` / `description` / `content` / `filePath`，我们自己构造 `Skill` 对象喂进去就行（已实测可用）。

渐进式披露的机制值得说明白：系统提示词里**只有名字和描述**，正文要模型自己用 `read` 工具去读 `<location>`。所以 skill 正文再长也不占常驻上下文。但模型不一定每次都会去读，需要靠提示词强调，或者提供 `/skill:name` 让用户强制加载。

### 4.6 MCP

pi **完全没有 MCP**，`docs/usage.md:306` 明确列为 non-goal。这块要从零接，但工作量不大——**MCP 的工具描述和 pi 的 `AgentTool` 都用 JSON Schema，几乎是直通的**。

```ts
// kernel/mcp.ts —— 注意这也属于 kernel 层，因为要产出 pi 的 AgentTool
async function mcpToolsToAgentTools(client: McpClient, serverName: string): Promise<AgentTool[]> {
  const { tools } = await client.listTools()
  return tools.map((t) => ({
    name: `mcp__${serverName}__${t.name}`,   // 前缀命名空间，避免多 server 撞名
    label: t.name,
    description: t.description ?? '',
    parameters: t.inputSchema as TSchema,     // MCP 的 inputSchema 就是 JSON Schema
    execute: async (_id, params, signal) => {
      const r = await client.callTool({ name: t.name, arguments: params }, { signal })
      return { content: r.content, details: {} }   // MCP 的 content 结构与 pi 基本一致
    },
  }))
}
```

`mcp.json` 的**顶层 key 使用 `servers`**，不是 `mcpServers`：

```ts
interface McpServerEntry {
  type: 'stdio' | 'http' | 'sse'
  command?: string; args?: string[]; env?: Record<string, string>   // stdio
  url?: string; headers?: Record<string, string>                    // http/sse
  timeout?: number        // stdio 启动超时（秒），默认 30
  enabled: boolean
  lastTestResult?: { success: boolean; message: string; timestamp: number }
}
```

四个实现要点：

1. **慢连接不能阻塞启动。** 连接放到后台并设置启动超时，连上后再把工具追加进 `agent.state.tools`（这个数组是可写的）
2. **stdio 要把 `process.env.PATH` 合并进 env**，否则子进程找不到 `npx` / `node`
3. **禁用的 server 直接跳过**，不要连了再过滤
4. **连接测试**要有，结果存 `lastTestResult` 给设置界面显示——MCP 服务器配错是最常见的用户问题

> ⚠️ MCP 工具要参与 4.4 的权限判定。不能仅凭 `mcp__` 前缀在 plan 模式下全部放行，至少要按 server 配置是否可信以及方法是否只读来判断。

## 5. 多 Agent 编排（新增部分）

pi **没有任何 subagent 机制**——根 README 明确把它列为 non-goal。但 `Agent` 类轻到可以直接并发 new：构造函数只做字段赋值 + 两个队列，无 I/O、无全局注册表，每个实例有独立的 `activeRun` / `AbortController` / listeners / state。

> pi 官方的 subagent 扩展是用 `child_process.spawn` 起子进程的——那是 CLI 场景的做法。我们在 Electron 主进程里当库用，**同进程 `new Agent()` 就行**，不用序列化跨进程传消息。

### 5.0 产品概念：专家（Expert）

面向用户的入口是「专家」，不是「子 Agent」。一个专家 = 一份人格 + 一套能力绑定：

```ts
interface Expert {
  id: string
  name: string                  // "小红书运营专家" / "资深合同法务专家"
  avatar?: string
  systemPrompt: string          // ★ 唯一必填项

  // 以下全是可选的能力绑定，不配就继承主会话
  model?: { channelId: string; modelId: string }
  tools?: string[]              // 工具白名单
  skills?: string[]             // 绑定的技能（4.5）
  mcpServers?: string[]         // 绑定的连接器（4.6）

  /** false = 只换 systemPrompt（共享上下文）；true = 独立子 Agent（隔离上下文） */
  isolated?: boolean
}
```

> **专家不只是人格，它是能力的作用域。** 这一点容易被低估，但它是规模化的答案：
>
> 技能和工具的 schema 都常驻上下文。平铺给同一个 Agent 时，能力越多提示词越重——
> 见过一个生产系统把 146 个技能全部装载进 system prompt，光技能就吃掉 50–80K token，
> 结果模型选不动，只好在前面再糊一层意图路由器去补救（**路由器是缺失分层的代偿**）。
>
> 有了专家层，「小红书运营专家」只绑 5 个社媒技能，「合同法务专家」只绑 3 个法务技能。
> 技能库涨到 500 个，单次会话的技能开销依然恒定。工具同理。

**关键设计：一个专家有两种运行方式，判断依据只有一条——是否需要独立上下文。**

| | 轻量模式（`isolated: false`） | 子 Agent 模式（`isolated: true`） |
|---|---|---|
| 实现 | `agent.state.systemPrompt = expert.systemPrompt` | `new Agent({ initialState: {...} })` |
| 上下文 | 共享当前会话 | 完全隔离，只看到派发给它的任务描述 |
| 成本 | 零 | 一份独立的上下文 |
| 适用 | 换人格、换知识重点、换输出风格 | 需要并发、需要上下文隔离、需要不同模型/工具 |
| 例子 | 「小红书运营专家」 | 「交易分析团队」的各个成员 |

#### 专家如何绑定能力

构建提示词时按名字过滤，`formatSkillsForSystemPrompt` 吃的本来就是数组：

```ts
const visible = allSkills.filter((s) => expert.skills?.includes(s.name) ?? true)
agent.state.systemPrompt = expert.systemPrompt + formatSkillsForSystemPrompt(visible)
agent.state.tools = resolveTools(expert)   // 同一套机制
```

三个已定的细节：

**① 绑定用名字列表，不用标签。** 名字列表精确，标签容易误绑；`group` 字段将来可以作为糖补上，但第一版只做名字列表。

**② `/skill:xxx` 手动调用可以突破绑定。** 绑定的语义是「默认给模型看什么」，不是「禁止使用什么」——这跟权限是两回事。用户显式调用就该加载。

实现上不用额外做：`formatSkillInvocation(skill)` 是把正文直接注入本轮 prompt，不依赖 system prompt 里列没列过它。

**③ 中途切专家：允许，但要插一条 `custom_message`。**

切换本身零成本（`state` 字段可写），但有两个后果：

- **击穿 prompt cache**：system prompt 变了，前缀缓存全部作废。频繁切换的用户会感知到成本跳动
- **历史里有对已移除工具的调用记录**：模型看到自己上一轮用过 `bash`，很可能会再试一次

所以切换时往会话里插一条 `custom_message`：

> 已切换到「合同法务专家」，可用能力已更新。之前可用的部分工具在当前专家下不可用。

这条消息**既是 UI 上的分隔标记，也是给模型的提示**——正好是 `custom_message` 这个 entry 类型的用途（应用注入、进 LLM 上下文、带 `display` 标志）。会话存储设计里已有这个类型，不用新增。

比「切专家必须开新会话」体验好，比放任不管可靠。

**pi 在这件事上比 Claude Agent SDK 顺手**，因为 `AgentState` 的字段是**可写的普通属性**：

```ts
agent.state.systemPrompt = expert.systemPrompt
agent.state.tools = resolveTools(expert)      // 运行时改工具集完全没问题
agent.state.model = resolveModel(expert)
```

pi 允许直接创建独立 `Agent` 实例，子 Agent 的模型、工具和 systemPrompt 可以按任务单独配置。

### 5.0.1 团队（Team）

截图里的「交易分析团队」说明专家还能组队。团队就是一组专家 + 一个编排策略：

```ts
interface ExpertTeam {
  id: string
  name: string
  members: string[]                          // expert id 列表
  strategy: 'parallel' | 'chain' | 'router'
}
```

| 策略 | 语义 |
|---|---|
| `parallel` | 同一任务丢给所有成员，各自独立产出，最后汇总 |
| `chain` | 流水线，前一个的输出作为后一个的输入 |
| `router` | 先由一个调度者判断该派给谁，再单点派发 |

团队成员**必须是 `isolated: true`**——共享上下文的话并发就没意义了，而且会互相污染。

存储放在 `~/.tgbuddy/experts/`：

```
experts/
├── index.json                   # 专家与团队的索引
├── {expert-id}.json             # 单个专家配置
└── prompts/{expert-id}.md       # systemPrompt 正文（长文本单独存，方便编辑和 diff）
```

> **实施顺序建议**：先做 `isolated: false` 的轻量专家（就是切 systemPrompt，一天能做完，用户马上能感知到价值），再做子 Agent，最后才做团队。别一上来就搞编排。

> **「召唤更多专家」**（截图右下角）是专家市场/导入，精简版先不做，但配置格式要预留：专家目录做成可以整个文件夹导入导出。

### 核心思路：子 Agent 包装成父 Agent 的一个工具

```ts
// tools/spawn-agent.ts —— 骨架，细节留给你填
const spawnAgentTool: AgentTool = {
  name: 'spawn_agent',
  label: '派发子任务',
  description: '把一个独立的子任务交给专门的子 Agent 处理',
  parameters: Type.Object({

    task: Type.String({ description: '给子 Agent 的完整任务描述，它看不到父会话的上下文' }),
    mode: Type.Optional(Type.Union([Type.Literal('single'), Type.Literal('parallel'), Type.Literal('chain')])),
  }),
  execute: async (toolCallId, params, signal, onUpdate) => {
    // TODO: 从 registry 取 role 对应的 systemPrompt / 允许的工具集 / 模型
    // TODO: new Agent({ ... })，订阅事件转发到 UI（带 parentToolCallId）
    // TODO: 注册到 orchestrator 的 childAgents，让父 abort 能级联
    // TODO: await sub.prompt(params.task)
    // TODO: 取 sub.state.messages 最后一条 assistant 的 text 作为返回
    // TODO: 累计 usage 到全局预算
  },

```

### 四个必须想清楚的设计点

**(1) 权限继承——子 Agent 的工具要不要弹 UI？**

子 Agent 的 `beforeToolCall` **继承父会话的白名单但不能弹新窗口**——命中白名单就放行，没命中就直接 block 并把 reason 告诉子 Agent（"该操作需要用户授权，请改用只读方式或向父任务报告"）。

这比无脑 allow 安全，也比弹窗死锁友好。真需要授权时，让子 Agent 把请求冒泡回父 Agent 由用户统一处理。

**(2) 事件路由——UI 里怎么嵌套显示？**

子 Agent 的每个事件转发时必须带 `parentToolCallId`。UI 先收集父工具调用 id，再把匹配的子活动收进 `childrenMap`。

我们的 `AgentStreamPayload` 加一个可选字段就行：

```ts
type AgentStreamPayload =
  | { kind: 'agent_event'; event: NormalizedEvent; parentToolCallId?: string }
  | { kind: 'host_event'; event: HostEvent }
```

**(3) 预算——这是多 Agent 场景的生死线**

pi 的 agent loop 没有 max turns，是个裸的 `while(true)`。单 Agent 时还能靠人看着，多 Agent 并发时必须有硬性上限：

```ts
interface RunBudget {
  maxTurns: number         // 每个 Agent 的轮次上限
  maxTotalTokens: number   // 整棵 Agent 树的 token 上限
  maxCostUsd: number       // 成本上限
  maxDepth: number         // 嵌套深度，建议 2（父 → 子，不允许孙）
  maxConcurrent: number    // 并发子 Agent 数，建议 3-5
}
```

实现挂在 `afterToolCall` 里返回 `terminate: true`，或者直接 `agent.abort()`。

`Agent` 类的 `AgentOptions` **没有暴露 `shouldStopAfterTurn`**（只有直接用低层 `agentLoop()` 才能设），所以轮次计数要靠 `afterToolCall` 或 `prepareNextTurn` 自己数。

**(4) 取消传播**

父 `abort()` 必须级联到所有在跑的子 Agent。orchestrator 维护 `Map<sessionId, Set<Agent>>`，stop 时遍历 abort。

注意 pi 的 `beforeToolCall` 拿到 signal 但**你有责任自己 honor abort**——用户点停止时你那个等待 UI 确认的 Promise 必须自己 resolve，否则挂死。

### 三种编排模式

| 模式 | 语义 | 实现 |
|---|---|---|
| `single` | 派发一个子 Agent，等它做完 | `await sub.prompt(task)` |
| `parallel` | 同一任务的多个角度并发，结果一起返回 | `Promise.all`，受 `maxConcurrent` 限制 |
| `chain` | 前一个的输出作为后一个的输入 | 串行 for 循环，中间结果拼进下一个 task |

先只实现 `single`，跑通了再加另外两个。

## 6. 四个基础工程骨架

这四个跟内核无关，是纯工程价值，建议原样搬：

### 6.1 事件传输的双通道

事件传输使用两条正交通道：

```ts
type AgentStreamPayload =
  | { kind: 'agent_event'; event: NormalizedEvent }  // 内核说的话
  | { kind: 'host_event'; event: HostEvent }         // 宿主自己的事件
```

把"内核原生消息"和"宿主自己的交互事件"（权限、AskUser、重试、标题生成）在传输层就分开。以后再换内核时，只需要动 `agent_event` 那一半。

### 6.2 权限交互的挂起模式

`Map<requestId, { resolve, request }>` 把 Promise 的 resolve 函数存起来跨 IPC 边界持有：

```ts
beforeToolCall: async ({ toolCall, args }, signal) => {
  if (isWhitelisted(sessionId, toolCall.name, args)) return undefined  // 放行
  if (isReadOnlyTool(toolCall.name, args)) return undefined

  const request = buildRequest(sessionId, toolCall, args)
  sendToRenderer(request)

  return new Promise((resolve) => {
    pending.set(request.id, { resolve, request })
    signal?.addEventListener('abort', () => {
      if (pending.delete(request.id)) resolve({ block: true, reason: '操作已中止' })
    }, { once: true })
  })
}
```

配套三个逃生口，一个都不能少：

1. **AbortSignal** 触发时自动 block
2. **会话结束**时批量 resolve 掉所有 pending（`clearSessionPending`）
3. **渲染进程 reload 后**能用 `getPendingRequests()` 把挂起的请求捞回来

> pi 的 `beforeToolCall` 有个天然的好性质：parallel 模式下工具的 preflight 是**串行**的，所以确认弹窗不会同时弹一堆，一个一个来。

#### ⚠️ 事件顺序的坑（阶段 1 实测确认）

**`tool_execution_start` 比 `beforeToolCall` 早约 5ms 触发。** 实测时序：

```
+  954ms  事件 tool_execution_start      ← 先发了"开始执行"
+  959ms  beforeToolCall 进入            ← 才开始问用户
+ 1472ms  beforeToolCall 返回（等了 500ms）
+ 1474ms  execute() 真正执行
+ 1474ms  事件 tool_execution_end
```

也就是说，**如果 UI 直接拿 `tool_execution_start` 渲染"正在执行 X"，用户会先看到"正在执行"，然后才弹出授权框**——看起来像是没经过同意就动手了，体验和信任感都很糟。

正确做法：工具活动的展示状态要由 `tool_execution_start` **和待授权队列共同决定**。同一个 `toolCallId` 存在 pending 权限请求时，渲染成「等待授权」而不是「执行中」。

> 这是 pi 事件顺序带来的约束，必须在 UI 状态机中处理。

**好消息**：拒绝时 `tool_execution_end` 会正常触发并带 `isError: true`（实测确认），所以 UI 上不会留下一条永远转圈的悬挂记录，不用自己补收尾逻辑。

### 6.3 generation 令牌式的并发守卫

被真实 bug 打磨出来的三条，任何有异步初始化的流式系统都会踩：

```ts
// ① 抢占槽位必须在第一个 await 之前，否则并发调用会在 await 间隙绕过入口检查
const runGeneration = Date.now()
activeSessions.set(sessionId, runGeneration)

// ② 释放时校验 generation，防止旧流的 finally 误删新流的注册
const release = () => {
  if (activeSessions.get(sessionId) !== runGeneration) return
  activeSessions.delete(sessionId)
}

// ③ 用户主动停止用单独的 Set 标记，在所有终态统一消费
//    （不能只靠 catch —— 中断后内核不一定走异常路径）
stoppedBySessions.add(sessionId)
```

### 6.4 提示词的静态/动态二分

- **静态**（`buildSystemPrompt`）——吃 prompt caching，会话期间不变
- **动态**（`buildDynamicContext`）——每条消息实时读盘，配置改了下一条消息就生效

动态部分注入当前时间（含时区和分钟）、工作区状态和工作目录。

pi 完全没有内置 prompt 拼装，`agent.state.systemPrompt` 就是个 string，默认空。所以这块从零写，但也因此完全自由。

### 6.5 工具结果与产物识别

> **⚠️ 已修订**：原设计要求「所有工具在 `details` 里写 `path` / `action`」。
> 实际改用 pi 内置的 `read`/`write`/`edit`/`bash` 之后这条**不成立**了 ——
> pi 的 `write` 返回 `details: undefined`，`edit` 返回 `{ diff, patch, firstChangedLine }`，
> 都不带路径。**我们无权规定第三方工具的返回形状。**
>
> 现在的做法见本节末尾「产物从调用参数推导」。

#### 双通道本身仍然成立

界面是三栏布局，第三栏是**结果区**（本次会话的产出），详见 [03-UI设计需求清单](03-UI设计需求清单.md) 屏幕 1。

要支撑结果区，工具必须区分「给模型看的」和「给界面用的」。**pi 的工具结果天然就有这个双通道**：

```ts
interface AgentToolResult<T> {
  content: (TextContent | ImageContent)[]   // 进 LLM 上下文
  details: T                                 // 应用自定义，模型看不到
  terminate?: boolean
}
```

所以每个会产生副作用的工具都要这样写：

```ts
// write 工具
return {
  content: [{ type: 'text', text: '已写入 config.ts（1.2 KB）' }],
  details: { path: '/abs/path/config.ts', bytes: 1234, action: 'create' },
}
```

**结果区读 `details`，模型读 `content`，互不干扰。**

配套的两条设计：

1. **产物索引从工具结果派生，不单独存状态。** 结果区就是对会话内工具调用的一个投影——扫 JSONL 里的工具结果，收集所有带 `path` 的 `details`。这样没有需要同步的第二份状态，会话回放时产物列表自然重建
2. **我们自己写的工具**（`delete` / `glob`）仍然遵守 `ToolDetails` 约定，`shared/types/message.ts` 里统一定义

#### 产物从调用参数推导 ★ 现行做法

既然管不了第三方工具的 `details`，就换个**不依赖它**的信息源：**工具调用的参数**。

```ts
// ① 从 assistant 消息里收集 toolCallId → path
for (const block of assistantMessage.content) {
  if (block.type === 'toolCall' && PRODUCING.has(block.name)) {
    callPaths.set(block.id, block.arguments.path)
  }
}
// ② 再看哪些调用真的成功了 —— isError 的不算产物
```

三个好处：不依赖任何工具的返回形状；换工具实现不用改；**从落盘消息重算**，所以重启后自然正确，「编辑并重发」截断历史时计数也会自动回退。

代价是要维护一份「哪些工具会产生产物」的名单（现在是 `write` / `edit`）。加新工具时别忘了登记 —— 这是把「每个工具都要遵守约定」换成了「一处集中登记」，后者更难忘。

#### 沙箱在 `ExecutionEnv` 层，不在工具层

同样的道理：**pi 的所有内置工具只能通过 `ExecutionEnv` 碰磁盘**，所以包一层 `SandboxedExecutionEnv`（`tools/sandboxed-env.ts`）就覆盖全部工具，不用指望每个工具记得调路径校验。

用 `Proxy` 而不是逐个方法转发，是为了 pi 将来给 `ExecutionEnv` 加新方法时**默认也走校验**，而不是静默漏掉。

> ⚠️ **一个必须知道的不对称**：沙箱对文件类工具是**硬约束**，对 `exec`（bash）只是**软约束**。
> 任意 shell 命令无法静态解析出会碰哪些文件。bash 的实际防线是「非只读命令每次都要授权」
> ＋「破坏性命令不可持久化」＋「系统级工具黑名单」，不是路径检查。

#### 这个沙箱防的是什么

**防模型犯错，不防攻击。** Agent 跑在 Electron 主进程里，进程权限一点没变；真要隔离得上容器或虚拟机（pi 官方文档也这么建议）。

它买到的是四样：模型幻觉出一个路径时能拦住；用户说「清理临时文件」而模型理解成整个 home 目录时能拦住；**`~/.tgbuddy` 在黑名单里，Agent 改不了自己的配置、历史和权限规则**（否则整套权限系统会被自己瓦解）；`.ssh` / `.aws` 在黑名单里，用户手滑点了「允许」也读不到私钥。

准确的说法是：**沙箱让「允许」这个按钮的后果变得可预测** —— 最坏情况是工作区里乱掉，而不是家目录被翻个底朝天。这个价值是真的，但它不叫安全隔离。

### 6.6 错误与重试 —— pi 完全没有，必须自建

这块是设计里最后一个空白，补上。

**pi 的 `Agent` 类不带任何重试。** 重试逻辑在 `AgentHarness` 层（0.81.1 才加的 `retry_scheduled` / `retry_attempt_start` / `retry_finished` 事件），而我们不用 harness。

本项目没有 SDK 子进程，重试策略保持保守，避免把配置或认证错误掩盖成漫长等待。

#### 错误分三类，处理方式完全不同

| 类别 | 例子 | 处理 |
|---|---|---|
| **可重试** | 429 限流、5xx、网络超时、连接重置 | 指数退避自动重试，UI 显示「第 N 次重试」 |
| **不可重试** | 401 认证失败、404 模型不存在、400 请求格式错 | 立即停，把原始错误文本给用户看 |
| **用户中止** | 用户点了停止 | 不是错误，不报警不重试 |

**判别依据**：pi 的 `error` 事件带 `reason: 'error' | 'aborted'`，`aborted` 直接归第三类。剩下的要从 `errorMessage` 里抠状态码——阶段 1 实测 DeepSeek 返回的是 `401: {"message":"Authentication Fails..."}` 这种形状，即**状态码在文本开头**。

> ⚠️ 别把不可重试的错误也退避重试。401 重试 25 次只会让用户多等两分钟，然后看到同一条错误。

#### 实现位置

pi 的 `agent.prompt()` 是个 Promise，重试包在**外面**，不要试图钻进 agent loop：

```ts
for (let attempt = 1; attempt <= MAX_RETRIES + 1; attempt++) {
  const err = await runOnce()          // 订阅 error 事件收集结果
  if (!err || !isRetryable(err)) break
  emitHostEvent({ type: 'retry', attempt, maxAttempts: MAX_RETRIES, reason: err.message })
  await backoff(attempt, abortSignal)  // ★ 退避必须能被 abort 打断
}
```

三个要点：

1. **退避等待必须能被 abort 打断。** 用户点停止时不该还在等 8 秒
2. **重试要发 `host_event`，不是 `agent_event`。** 重试是宿主行为，内核不知道自己被重试了——这正是双通道设计的价值
3. **重试前要清理半截的流式状态。** 上一次可能已经吐了半句话到 UI，重试时要么续着写要么清掉，别拼接出乱码

#### 建议参数

```ts
const MAX_RETRIES = 3
const BASE_DELAY_MS = 1_000
const MAX_DELAY_MS = 15_000        // 指数退避封顶
```

三次退避总共约 7 秒。真连不上就该告诉用户，而不是默默重试两分钟。

| **1** | **打通内核** | `kernel/models.ts` + 一个 Node 脚本 | 命令行里能跟一个国内端点的模型对话，流式输出打印到终端 |

## 9. 接国内端点的备忘

`baseUrl` 在 **Model 上**，`apiKey` 在 **auth 或 per-request options 上**：

```ts
import { createModels, createProvider, type Model } from '@earendil-works/pi-ai'
import { openAICompletionsApi } from '@earendil-works/pi-ai/api/openai-completions.lazy'

const model: Model<'openai-completions'> = {
  id: 'deepseek-chat', name: 'DeepSeek Chat',
  api: 'openai-completions', provider: 'my-gateway',
  baseUrl: 'https://api.deepseek.com/v1',          // ← baseUrl 在 model 上
  reasoning: false, input: ['text'],
  cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
  contextWindow: 128000, maxTokens: 8192,
  compat: { /* 见下 */ },
}

const models = createModels()
models.setProvider(createProvider({
  id: 'my-gateway',
  auth: { apiKey: { name: 'API Key', resolve: async () => ({ auth: {} }) } },
  models: [model],
  api: openAICompletionsApi(),
}))

// per-request 直接给 key，永远优先于 provider 解析
await models.complete(model, ctx, { apiKey: decrypt(channel.apiKey) })
```

`Model.compat` 是接第三方端点时最容易踩坑的地方：

```ts
compat: {
  supportsDeveloperRole?: boolean      // vLLM / Ollama / SGLang 通常要 false
  supportsReasoningEffort?: boolean
  maxTokensField?: 'max_completion_tokens' | 'max_tokens'
  requiresToolResultName?: boolean
  requiresThinkingAsText?: boolean
  thinkingFormat?: 'openai' | 'deepseek' | 'zai' | 'qwen' | ...
  cacheControlFormat?: 'anthropic'
  supportsStrictMode?: boolean
}
```

不设 `compat` 时 pi 会按 baseUrl 做 URL 探测，但第三方网关经常探测不准，建议显式配。

Anthropic 兼容端点同理，换成 `api: 'anthropic-messages'` + `anthropicMessagesApi()`。

**两个 Electron 特有的坑**：

1. **环境变量**：GUI 启动的 Electron 拿不到 shell 里的 `ANTHROPIC_API_KEY` 等。用 per-request `apiKey`，别依赖 `process.env`。
2. **代理**：`http-proxy-agent` / `https-proxy-agent` 是 pi-ai 的直接依赖，读 `HTTP_PROXY` / `HTTPS_PROXY`。国内环境这个很有用。

## 附：不采用的设计

换内核之后这些全部作废，别浪费时间研究：

1. **fork / rewind 文件检查点**——直接解析了 SDK 私有的 `file-history` 目录布局，全代码库最深的耦合
2. **MessageChannel（长生命周期 AsyncGenerator）**——纯粹为绕开 SDK `streamInput()` 会关 stdin 的行为而写
3. **`resolveSDKCliPath()` 子进程管理**——SDK 是个 214MB native binary 才需要
4. **`buildSdkEnv()` 里对 `ANTHROPIC_*` 的大扫除**——对抗 SDK 版本间语义反复横跳的创伤产物
5. **`sdkSessionId` / resume / `resumeSessionAt`**——pi 里就是传消息数组
6. **提示词里的 SDK 特有工具名**——`TaskCreate` / `EnterPlanMode` 这些要换成我们自己的工具名
   （注意：**计划模式本身是要做的**，见 4.4；作废的只是 SDK 的工具名和 `permissionMode` 枚举值）
