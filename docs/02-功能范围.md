# 功能范围

基于 WorkBuddy 的界面参考，逐项判断做 / 不做。原则：**先把核心闭环跑通，外围一律推迟。**

判断标准就一条——**去掉它，Agent 还能不能完成一次有价值的任务？** 能，就推迟。

---

## 一、必做（缺了核心闭环不成立）

### 1.1 权限模式与确认 UI

参考图里的气泡做得很好，值得照抄这个形态：

> 当前为默认权限，所有操作都会在安全沙箱约束内进行，超出范围会请求你的允许。
> [ 允许完全访问 ○ ]

一句人话说清楚当前状态 + 一个开关切到完全访问。比一个写着 `auto / plan / bypass` 的下拉好懂得多。

对应设计文档 4.4。**这是 pi 上必须自建的第一优先级**——pi 明确声明不带任何权限系统，默认以宿主进程权限运行。

### 1.2 上下文用量面板 ★ 被低估的功能

参考图：

```
43.1%  已使用 72.5K / 168.0K
  系统提示词      ~9.7K
  工具及子智能体   ~25.3K     ← 注意这个
  对话消息        ~36.1K
  连接器及 MCP     ~103
  技能            ~1.2K
```

**「工具及子智能体」占了 35%，快赶上对话消息了。** 这一个数字就论证了为什么专家要绑定工具子集，而不是把所有工具一股脑塞进去。

所以这个面板不只是给用户看的，**它是我们自己调优的仪表盘**。建议早做，别等到阶段 6。

用 pi 做特别便宜，因为两个前提都已经满足：我们自己持有 `agent.state.messages` 数组，pi 又给了精确的 token 会计（`usage.input / output / cacheRead / cacheWrite / totalTokens`）。分类统计各段占用是纯计算，不需要额外请求。

它同时是阶段 6 压缩的触发依据——`shouldCompact` 要的就是这个数。

### 1.3 技能选择器（`/`）

参考图是 `技能 (18)` + `指令 (2)` 的分组列表，带图标、描述、置顶。

pi 直接支持：`formatSkillInvocation(skill, args)` 生成显式调用的 prompt。我们只需要做列表 UI 和触发。

**精简**：先做列表 + 选择 + 参数，**不做置顶**（`pin`）。

> 注意参考图里 `NeoData金融搜索服务` 的图标和其它技能不同——那是 MCP 提供的能力混在同一个列表里。这个设计是对的：**用户不该关心一个能力来自技能还是连接器**，统一入口。我们的选择器也应该合并展示，但内部要区分来源。

### 1.4 沙箱：文件路径 + 命令前缀

参考图的「安全中心 → 沙箱安全」拆成三块，前两块必做：

| | 做法 |
|---|---|
| **文件安全** | 路径白名单 / 黑名单。默认只允许工作区目录 |
| **命令安全** | 命令前缀的「询问」与「放行」名单 |
| 网络安全 | 推迟。URL 域名规则等有 `web_fetch` 工具了再说 |

**这是 pi 上必须从零建的**。设计文档里对应 `tools/sandbox.ts`。

命令前缀判定要复用 4.4 里那条经验：**匹配只读命令时必须排除 `node` / `python` / `ruby` / `perl` / `php` 这些解释器**，否则 `python -c "os.remove(...)"` 直接绕过。

### 1.5 删除保护 → 回收站 ★ 性价比最高的一条

参考图：

> 删除保护：开启后优先移到废纸篓/回收站，关闭后按系统删除
> 批量删除审批：一次删除达到该数量时需要审批 [ 50 ]

**成本极低，价值极高。** 误删是 Agent 最容易造成的不可逆伤害，而 pi 一点保护都不给。

实现就是删除类工具默认走系统回收站 API 而不是 `unlink`，再加一个数量阈值触发审批。半天的工作量，换掉一整类灾难。

**必做，而且建议提前到阶段 4 跟权限一起做。**

### 1.6 渠道 / 模型配置表单

参考图的「添加模型」对话框**几乎就是 pi 的 `Model` 类型**，照抄这个结构我们的配置界面就有了：

| 参考图字段 | 对应 pi |
|---|---|
| 接口地址 | `Model.baseUrl` |
| API Key | 我们自己的 `Channel.apiKey` |
| 模型名称 | `Model.id` |
| 工具调用 | （pi 只收录支持工具调用的模型，恒为真） |
| 图片输入 | `Model.input: ['text', 'image']` |
| 思考模式 / 仅思考 / 允许关闭思考 | `Model.reasoning` + `compat.thinkingFormat` |
| 自定义协议 | `Model.compat` 的其余项 |
| 默认思考强度 / 支持的思考强度 | `Model.thinkingLevelMap` |
| 输入 / 输出 token | `contextWindow` / `maxTokens` |

另外参考图把配置文件路径直接暴露给用户（`%USERPROFILE%\.workbuddy\models.json`），这符合本地优先原则，我们也这么做——`~/.tgbuddy/channels.json`，并在界面上给一个「打开配置文件」。

**但有一处要比它做得好**：参考图的提供商下拉是硬编码的几家。我们应该**从 pi 的模型目录里读**——`node_modules/@earendil-works/pi-ai/dist/providers/data/*.json` 有 36 家的完整配置，选了提供商就自动填好 `compat` 和模型列表，用户只需要填 key。这是我们相对它的结构性优势。

## 二、该做，但可以晚（有更好，没有也能跑）

### 2.1 附件

参考图：`添加文件 → 本地文件 / 腾讯文档`，以及 `引用对话中的文件`。

- **本地文件**：做。但**先只支持纯文本和图片**
- **Office / PDF 解析**：推迟。这需要引入 `pdf-parse` / `officeparser` / `word-extractor` 等依赖，属于典型的"值得做但不该现在做"
- **腾讯文档**：丢弃。第三方文档集成跟架构学习无关

`引用对话中的文件` 这个交互值得记一笔：让用户 `@` 之前对话里出现过的文件，避免重复上传。实现上就是从会话 JSONL 里扫附件记录，成本不高。

### 2.2 记忆 —— 这里有个范式分歧要先拍板

**记忆写入有两种不同范式，不是实现细节的差异：**

| | 自动提取 | 工具式写入 |
|---|---|---|
| 写入方式 | **代码自动从对话提取** | **模型主动调工具写** |
| 存储形态 | 一整段用户画像摘要 | 离散的记忆条目 |
| 更新 | 定期重新生成整段 | 增量追加单条 |
| 用户可控性 | 只能开关 | 可以单条查看/编辑/删除 |
| 注入成本 | 低（一段文字） | 取决于召回条数 |

参考图里那段摘要长这样：「**工作背景** 用户近期围绕三大核心方向开展调研：一是上海地区的中型互联网市场…」——是一段人物画像，不是事实条目。

**推荐工具式写入**，三个理由：

1. **代码零启发式**。不需要额外的后台提取任务，不需要判断"什么时候该提取"，模型自己决定
2. **可解释、可编辑**。用户能看到具体记了什么、单条删掉
3. **符合 pi 的形态**。pi 只要求内核支持自定义工具，这个门槛它满足；而自动提取需要我们自己排一条后台流水线

提示词必须明确：**「记忆工具是工具，不是文件操作！绝对不要把记忆写入 MEMORY.md」**，并把记忆定位为"我们一起经历过的事"而不是"关于用户的信息条目"。

记忆存储采用本地文件，不依赖云端服务。

**补两处**（来自生产级系统的记忆分层参考，详见 [01-架构设计.md](01-架构设计.md) 4.3）：

1. **每层都要有硬上限**——记忆召回条数、单条长度、压缩摘要字符数。没有上限的记忆会无声地吃掉上下文，而且因为注入在最前面，挤掉的是最近的对话
2. **记忆条目要分类**（profile / preference / project / history），召回时按场景取不同类

**丢弃**：「从其他 AI 导入记忆」。

### 2.3 指令 / Prompt 模板

参考图的 `/` 选择器里除了「技能 (18)」还有「指令 (2)」。

pi 的 harness 层有 `PromptTemplate` 概念和 `formatPromptTemplateInvocation`，可以直接用。但它和技能的边界有点模糊——**技能是给模型看的能力说明，指令是给用户用的 prompt 快捷方式**。

优先级低于技能。技能做完了再说。

### 2.4 专家与多 Agent 编排 —— 名词对照

容易混淆，这里把三层说清楚：

| 层次 | 名词 | 是什么 |
|---|---|---|
| **产品** | **专家 Expert** | 用户看到的。一份人格 + 一套能力绑定 |
| **产品** | **团队 Team** | 多个专家 + 一个编排策略（parallel / chain / router） |
| **实现** | `AgentTool` | pi 的工具接口。**子 Agent 是通过一个叫 `spawn_agent` 的 AgentTool 暴露给父 Agent 的** |

也就是说，「多 Agent 编排」在实现层面就是**一个工具**——父 Agent 调 `spawn_agent(role, task)`，工具的 `execute` 里 `new Agent()` 跑完再把结果作为工具返回值交回去。父 Agent 完全不知道自己在做编排，它只是调了个工具。

专家有两种运行方式，判断依据只有一条——**是否需要独立上下文**：

- **轻量专家**（`isolated: false`）：只切 `agent.state.systemPrompt`，共享当前会话，零成本
- **子 Agent 专家**（`isolated: true`）：`new Agent()`，独立上下文，可并发

团队成员必须是 `isolated: true`——共享上下文的话并发没意义，还会互相污染。

完整设计见 [01-架构设计.md](01-架构设计.md) 第 5 节。**排在阶段 8，但先做的阶段 7.5 轻量专家一天就能出效果。**

## 二·五、能力体系：内置 vs 用户提供

「技能」和「工具」的设置是同构的，都要区分**内置**和**用户添加**，但两者的来源和管理方式不同。

### 2.5.1 工具的三个来源

| 来源 | 例子 | 能否禁用 | 能否删除 |
|---|---|---|---|
| **内置工具** | `read` / `write` / `edit` / `bash` / `grep` / `find` | ✅ 可关 | ❌ 不可删 |
| **连接器（MCP）提供的工具** | `mcp__neodata__search` | ✅ 可关（连整个 server 关） | ✅ 可删 server |
| **子 Agent 工具** | `spawn_agent` | ✅ 可关 | ❌ 不可删 |

**为什么内置工具必须可关**：回看 1.2 那张上下文用量图——「工具及子智能体」占了 25.3K，是总量的 35%。**每个工具的 schema 都常驻上下文**。一个只需要读文件做分析的专家，把 `bash` / `write` / `edit` 塞给它是纯浪费，还扩大了攻击面。

所以工具开关不只是权限问题，**也是上下文预算问题**。

### 2.5.2 技能的两个来源

| 来源 | 位置 | 特点 |
|---|---|---|
| **内置技能** | 随应用分发，首次启动播种到 `~/.tgbuddy/default-skills/` | 有版本升级契约 |
| **用户技能** | 工作区的 `skills/` 目录 | 用户自己放、或从别处导入 |

**内置技能的 semver 契约**：

每个 `SKILL.md` 的 frontmatter 必须有 `version` 字段。应用启动时用 semver 比较决定是否把新版同步到用户目录。

> ⚠️ **改了技能内容就必须递增 version，否则老用户永远拿不到新内容。**
>
> 不要无条件 `cpSync`：每次启动同步大量文件会阻塞主进程。新增技能不需要先注入旧版本——「目标缺失即注入」会让老工作区自动获得。

**启停用靠目录搬家**，不改字段：

```
skills/{slug}/           # 启用中
skills-inactive/{slug}/  # 已停用
```

比在配置文件里存一个 enabled 列表更朴素，也不会出现"配置里有但目录没了"的不一致。

### 2.5.3 设置界面

技能和工具的设置页结构应该一致，都是**分组列表 + 开关**：

```
工具
  内置                          [全部启用 ▾]
    ☑ read      读取文件
    ☑ write     写入文件
    ☑ bash      执行命令
    ...
  连接器提供
    ☑ NeoData金融搜索  (3 个工具)
  子 Agent
    ☑ spawn_agent

技能
  内置 (5)                      [检查更新]
    ☑ tencent-docs-routing  v1.2.0
    ...
  工作区 (13)                    [+ 添加]
    ☑ westock-tool
    ...
```

每组显示**该组当前占用多少上下文 token**——这会让"关掉不用的工具"变成一个有依据的决策，而不是凭感觉。

> **给用户的入口**：截图里 `/` 唤起的选择器把技能和 MCP 能力**混在同一个列表**展示，这个设计是对的——用户不该关心一个能力来自技能还是连接器。但**设置页里要分开管**，因为它们的生命周期完全不同。

## 三、明确丢弃（至少这个阶段）

| 功能 | 为什么丢 |
|---|---|
| **腾讯文档等第三方集成** | 跟架构学习无关，纯业务对接 |
| **从其他 AI 导入记忆** | 迁移工具，不是核心能力 |
| **安全网关 / 传输加密** | 那是 SaaS 架构的需求。我们本地优先，没有云端，数据不出本机 |
| **内置运行时打包**（随包提供 Node/Python/Git Bash） | 体积和跨平台维护成本过高。我们**探测**而不是**打包** |
| **智能体邮箱** | 独立产品线 |
| **快捷键定制 / 个性化 / 主题** | 等真有人用了再说 |

> **多 Agent 编排没有被丢弃**，它是「专家」的一部分，只是排在最后。见下面 2.4。

### 关于「系统级工具」黑名单

参考图有一项：

> WSL、wmic、sc、reg、schtasks 等系统级工具可绕过沙箱限制，请谨慎启用 [ 禁用 ]

**这个要做**，但它不是独立功能，就是 1.4 命令前缀黑名单里的一条默认规则。一行配置的事，但漏了就等于沙箱形同虚设——这几个命令确实能绕过任何路径白名单。

### 关于运行时探测

虽然不打包运行时，但**环境探测必须做**，尤其在 Windows 上：需要检测 Bun、Git 和可用 Shell，并处理 Git Bash / PowerShell 的选择。

我们的 `bash` 工具在 Windows 上要能找到一个可用的 shell，这是刚需不是优化。

## 四、修订后的阶段顺序

原计划有调整：**上下文用量面板提前**（它是调优仪表盘），**删除保护并入阶段 4**（性价比太高）。

| # | 阶段 | 内容 |
|---|---|---|
| 1 | ✅ 打通内核 | 已完成 |
| 2 | Electron 骨架 | IPC 双通道，能发消息看到流式 |
| 3 | 归一化 + 持久化 | JSONL 树、原子写、续接 |
| 4 | 工具 + 权限 + **沙箱** + **删除保护** | 含路径白名单、命令前缀、回收站 |
| 4.5 | 计划模式 | |
| 5 | 并发与中断 | |
| 5.5 | ✅ **上下文用量面板** | 真实总占用 + 系统/工具/消息分类；压缩按钮阶段 6 开放 |
| 6 | 上下文压缩 | |
| 6.5 | 技能 + 连接器 | 含 `/` 选择器、内置技能的 semver 契约、工具/技能开关 |
| 7 | 记忆（工具式、本地） | |
| 7.5 | 专家（轻量：切 systemPrompt） | 一天出效果 |
| 8 | 专家（子 Agent）+ 团队编排 | 即 `spawn_agent` 工具 + parallel/chain/router |
| 9 | **Plan 2.0：结构化任务执行** | 宿主持有任务列表、依赖、退出条件、状态与验证证据 |

附件、指令、网络安全规则不进主线，等主线跑通再插。
