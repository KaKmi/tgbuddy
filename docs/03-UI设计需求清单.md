# UI 设计需求清单

给设计用的输入文档。**只列这个阶段真正需要的屏幕**——它们的状态模型会反向决定后端的 IPC 契约和数据结构，必须先定。

其余界面（设置页、专家管理、团队编排）等做到对应阶段再设计，现在画等于对着不存在的功能画图。

产品形态：Electron 桌面应用，只有 Agent 模式（没有普通聊天模式）。视觉风格参考 WorkBuddy —— 卡片和阴影取代边框，克制的留白。

---

## 屏幕 1：主窗口布局 —— 已定：三栏，第三栏是结果区

**布局：侧边栏 · 对话区 · 结果区**（与 WorkBuddy 一致）。

第三栏**是「结果区」，不是文件树**。理由：

Agent 应用有个固有矛盾——**对话区展示的是过程，用户真正要的是产物**。一次任务几十个工具调用滚过去，最后生成的那份报告、那张图、那个改好的文件会被埋在工具噪音里。文件树解决不了这个问题，它展示的是目录结构，不是"这次任务产出了什么"。

结果区的语义是「本次会话的产出」，按产生顺序排列，点开预览。文件树可以作为它的一个模式，但不是默认。

### 还需要在原型里定的

1. **产物如何组织**：时间顺序？按类型分组？只显示最终产物还是包含中间产物？
2. **预览支持哪些类型**：markdown 渲染 / 代码高亮 / 图片 / HTML 直接渲染？
3. **能否编辑**：只读预览，还是可以直接改？
4. **★ 空状态**：大多数会话开始时结果区是空的，**这个状态出现频率最高**，别当边缘情况处理
5. 顶部工具栏：参考图里输入框上方是「模式」「专家」「技能」「连接器」四个入口 + 模型选择 + 上下文百分比
6. 无任何会话时的整窗空状态

### 对后端的影响（三条，都要在阶段 4 之前定好）

**① 产物索引从工具结果派生，不单独存状态。**

每次 `write` / `edit` 执行时记录碰过的路径，结果区就是对会话内工具调用的一个投影。这样没有需要同步的第二份状态，会话回放时产物列表自然重建。

**② ★ pi 的工具结果天然有我们需要的双通道 —— 这条要在写第一个工具之前立好规矩。**

```ts
interface AgentToolResult<T> {
  content: (TextContent | ImageContent)[]   // 进 LLM 上下文
  details: T                                 // 应用自定义，模型看不到
  terminate?: boolean
}
```

所以 `write` 工具应该这样返回：

```ts
return {
  content: [{ type: 'text', text: '已写入 config.ts（1.2 KB）' }],   // 给模型
  details: { path: '/abs/path/config.ts', bytes: 1234, action: 'create' },  // 给结果区
}
```

**结果区读 `details`，模型读 `content`，互不干扰。**

这个约定必须在阶段 4 写工具时就立住——后面补会很痛，所有工具都要回头改签名。

**③ 需要文件监听。** 产物可能被外部改动（用户自己编辑、其它进程写入），结果区要保持新鲜，后续实现 `workspace-watcher.ts`。

## 屏幕 2：工具活动卡片 ★ 最重要

一次工具调用在消息流里的完整呈现。这是 Agent 应用信息密度最高的地方，也是最容易做砸的地方。

**要回答的问题：**

1. **默认折叠还是展开？** 一次任务可能有几十次工具调用，全展开会淹没对话
2. **参数怎么显示？** `read({path: "..."})` 这种结构化参数，是显示原始 JSON 还是人话摘要（"读取 config.ts"）
3. **结果怎么显示？** 长输出（比如 grep 出 200 行）怎么截断，怎么展开
4. **★ 「等待授权」态长什么样？**

第 4 点是硬约束，必须在设计里体现：

> pi 的事件顺序是 `tool_execution_start` **早于** 权限询问约 5ms（阶段 1 实测确认）。
> 如果卡片直接按"开始执行"渲染，用户会先看到「正在执行 rm -rf ...」、然后才弹出授权框——
> 看起来像是没经过同意就动手了。
>
> 所以工具卡片至少有四态：**等待授权 / 执行中 / 成功 / 失败**，
> 且「等待授权」必须优先于「执行中」显示。

5. **子 Agent 的嵌套怎么显示？**（阶段 8 才做，但结构要预留）父 Agent 派发的子任务，其内部的工具调用要能收进一个可折叠的组里

## 屏幕 3：权限确认

**要回答的问题：**

1. **inline 卡片还是模态弹窗？** inline 不打断阅读但容易被划过去；模态强制响应但打断心流。Agent 可能连续请求多次授权
2. **需要展示什么？** 工具名、完整参数、将影响哪些文件、危险等级
3. **★ 「总是允许」的粒度是什么？** 这个直接决定白名单的数据结构，是最需要设计拍板的一条：

   - 「总是允许这个工具」（`read` 全部放行）
   - 「总是允许这个路径」（`~/project/**` 下的读写都放行）
   - 「总是允许这个命令前缀」（`git status` 放行，但 `git push` 仍要问）
   - 以上的组合？

   粒度太粗不安全，太细用户会被问烦。**建议至少支持「工具 + 命令前缀」两级**，这是参考图「命令安全：为命令前缀配置询问和放行名单」的做法。

4. **拒绝之后呢？** 给模型一句 reason 让它换方式（pi 的 `{ block: true, reason }` 就是这个语义）。UI 上要不要让用户填这句话？

5. **多个请求排队时怎么办？** 一次显示一个还是堆叠？（pi 的 preflight 是串行的，所以不会同时来一堆，但会一个接一个）

## 屏幕 4：上下文用量与压缩

用量面板参考图已经给了（分类进度条 + 五项占比），照做即可。需要补的是**压缩过程**：

1. 压缩是**自动发生**还是**需要用户确认**？
2. 压缩进行时，对话区显示什么？（这期间要调一次 LLM 生成摘要，有几秒延迟）
3. 压缩完成后，被折叠掉的历史消息**在界面上怎么呈现**？完全消失？还是留一条可展开的「已压缩 N 条消息」分隔线？

> **对后端的影响**：如果要能展开查看被压缩的历史，JSONL 里的原始消息就不能丢弃，
> 重建上下文时按 `firstKeptEntryId` 切分但保留全量。这影响 `session-store` 的读取接口设计。

## 屏幕 5：会话列表 ★ 有个架构问题要先答

**要回答的问题：会话需要分支 / 时间旅行吗？**

我们目前的设计选了 pi 的**会话树**格式——每条记录带 `id` / `parentId`，可以从任意历史点分叉出新分支，不新建文件。

好处是 fork、重新生成、回退到某条消息重来，全部零成本。

**但如果界面上永远不展示分支，这棵树就是纯粹的过度设计**，应该退回成简单的线性追加。

所以需要设计明确：

- 会话列表里要不要显示分支结构？
- 用户能不能「从这条消息重新开始」？
- 能不能 fork 一个会话去试另一条路？

**这个问题请优先回答**，它直接决定 `session-store` 的数据结构，而存储格式是最难中途改的东西。

其余需要明确的：置顶、归档、按日期分组、搜索、流式中的会话在列表里怎么标示。
