# 007 - TgBuddy 代码仓库设计

## Status

这是 TgBuddy 第一版的 Agent Runtime 与代码归属基线。产品语义仍以 `docs/01-架构设计.md`、`docs/02-功能范围.md` 和 `docs/06-设计决策.md` 为准；本文回答“消息如何进入 Agent Runtime、各组件负责什么、端口由谁实现、代码放在哪里以及谁可以依赖谁”。

当前实现已经建立公共 contract、`AgentRuntime` 门面、`RunCoordinator`、`AgentEngine` Port、`PiAgentEngine`、显式 Composition Root 和自动架构检查。R01 已完成 `AgentRuntime`、事件发布器与 Host Adapter 局部命名收口；R02 已完成 `StartRunInput`、`runs.start()` 与 `RunCoordinator.start()` 语义链。

## Summary

仓库采用“Agent Runtime 业务核心 + Port/Adapter + 显式 Composition Root”。Electron、Web Server 或未来 CLI 只是 Host Adapter；它们不能成为业务 owner。

```text
Renderer / Web Client
  -> Electron IPC / HTTP + SSE
    -> AgentRuntime
      -> RunCoordinator
        -> AgentEngine Port
          -> PiAgentEngine
            -> AgentHarness（@earendil-works/pi-agent-core）

AgentRuntime -> Persistence Ports -> SQLite / PostgreSQL / Blob
AgentRuntime -> ExecutionEnv Port  -> Filesystem / Sandbox / Worker
AgentRuntime -> MCP Port           -> stdio / HTTP Transport
```

- `shared/contracts` 保存跨进程、跨边界的可序列化 DTO、事件和 IPC map。
- `runtime` 拥有 AgentRuntime 门面、Session/Run/Context 语义、业务规则、用例、状态机和 Port，不知道 Electron、React、Node 文件系统、SQLite 或 pi。
- `kernel/pi` 实现 `AgentEngine` 等内核 Port，是 pi 运行时唯一边界；`AgentHarness` 只能从这里被创建和调用。
- `infrastructure` 实现 Repository、Store、Blob、ExecutionEnv、Secret 和 MCP Transport Port。
- `main` 只负责 Electron 生命周期、窗口、IPC 与依赖装配。
- `preload` 只把 typed IPC 暴露为 `window.tgbuddy`。
- `renderer` 只依赖 shared contract 和前端模块。

## 1. 依赖方向

```text
shared <- runtime
shared + runtime ports <- kernel/pi
shared + runtime ports <- infrastructure
shared + runtime public API + kernel/infrastructure factories <- main/bootstrap
shared + runtime public API <- main/ipc
shared <- preload
shared <- renderer
```

具体规则由 `scripts/check-architecture.ts` 执行：

| Source | Allowed targets | 关键禁止项 |
|---|---|---|
| `src/shared/**` | shared；两个指定 contract 的 pi type-only 例外 | runtime、kernel、infrastructure、main、Electron、React、Node runtime |
| `src/runtime/**` | shared、runtime | pi、Electron、React、Node runtime、kernel、infrastructure、main |
| `src/kernel/pi/**` | shared、runtime port、pi、必要 Node API | infrastructure、main、preload、renderer、Electron |
| `src/infrastructure/**` | shared、runtime port、必要 Node/Electron adapter API | kernel、main、preload、renderer、Runtime concrete service |
| `src/main/bootstrap/**` | shared、Runtime public API、factory、main 内部、Electron/Node | renderer、preload |
| `src/main/ipc/**` | shared、Runtime public API、纯 IPC helper、Electron | Runtime 内部、kernel、infrastructure、repository/store |
| Main lifecycle/window | shared、Runtime public API、main 内部、Electron/Node | renderer、preload、concrete repository |
| `src/preload/**` | shared、Electron context bridge | runtime、kernel、infrastructure、main、renderer |
| `src/renderer/**` | shared、renderer、前端 package | runtime、kernel、infrastructure、main、preload、Electron、Node runtime |

检查范围固定为 `src/**/*.{ts,tsx}`，排除 `.d.ts`、`dist/**` 和 `node_modules/**`。相对路径、`.ts/.tsx` 后缀、目录 `index.ts`、TypeScript paths 和 Vite alias 都必须解析。每条违规输出：

```text
source -> target -> violated rule
```

本地与 CI gate 使用：

```bash
bun run check:architecture
```

## 2. 公共契约

`src/shared/contracts` 按 workspace、session、run、message、event、permission、capability、artifact、channel、context 和 IPC 拆分。contract 必须可序列化，不得包含 Electron handle、数据库连接、文件描述符或 service 实例。

消息继续使用 pi 原始消息信封和 `kernel: 'pi@0.82'` 版本护栏，不增加往返翻译层。只有以下 type-only import 例外：

- `contracts/message.ts` 可引用 `@earendil-works/pi-ai` 和 `@earendil-works/pi-agent-core` 的消息类型。
- `contracts/events.ts` 可引用 pi 的 `StopReason` 与 `Usage`。

`IpcCommandMap` 是请求/响应的唯一类型来源。Preload 的友好 API 使用 `satisfies TgBuddyAPI` 校验，Main handler 使用同一 map 的 `IpcRequest` / `IpcResponse`。

## 3. Agent Runtime

### 3.1 对外门面

宿主只能通过 `AgentRuntime` 调用应用能力：

- `workspaces`
- `sessions`
- `runs`
- `permissions`
- `plans`
- `questions`
- `context`
- `artifacts`
- `capabilities`
- `settings`
- `subscribe(listener)`
- `dispose()`

门面由以下稳定签名创建：

```ts
interface AgentRuntime {
  workspaces: WorkspaceCommands
  sessions: SessionCommands
  runs: RunCommands
  permissions: PermissionCommands
  plans: PlanCommands
  questions: AskUserCommands
  context: ContextCommands
  artifacts: ArtifactQueries
  capabilities: CapabilityCommands
  settings: SettingsCommands
  subscribe(listener: AgentRuntimeEventListener): () => void
  dispose(): Promise<void>
}

function createAgentRuntime(
  dependencies: AgentRuntimeDependencies,
): AgentRuntime
```

`createAgentRuntime()` 只组合显式依赖，不读取模块级 service locator，不创建 Electron 窗口、数据库、文件系统或 pi 实例。业务事件统一通过 `AgentRuntimeEventListener` 发布，Host Adapter 只负责协议转换和事件转发。

### 3.2 命令语义

不同边界使用符合其意图的函数名：

| 边界 | 函数 | 语义 |
|---|---|---|
| Renderer / Preload | `agent.send(input)` | 用户发送一条消息 |
| Main IPC | `agentRuntime.runs.start(input)` | 把消息翻译为一次 Run 的启动命令 |
| Runtime | `RunCoordinator.start(input, emit)` | 建立并编排一次 Run |
| Kernel Port | `AgentEngine.run(invocation, signal)` | 执行内核并产生事件流 |
| pi Adapter | `AgentHarness.prompt(text)` | 进入 pi 的模型与 Tool 循环 |

`send` 不得继续作为 Runtime/Coordinator 的运行生命周期术语；`run` 不得用作 Host Adapter 的消息动作。

### 3.3 RunCoordinator

`RunCoordinator` 是 Agent Runtime 内部的一次 Run 调度器，负责：

1. 通过 `RunRegistry` 保证同一 Session 单飞、不同 Session 可并行；
2. 分配 `runId`、`AbortController` 和 active-run 生命周期；
3. 调用 invocation factory 获得本次 Run 的不可变输入快照；
4. 调用 `AgentEngine.run()` 并把 `AgentEvent` 包装为带 `sessionId/runId/channel` 的 `StreamFrame`；
5. 推进 Session 的 `running -> done | failed | interrupted` 状态；
6. 观察 Turn usage、调用 Context guard，并在结束后触发 Context 收尾；
7. 统一处理拒绝重入、主动停止、内核错误、缺失 `run_end`、Session 收尾失败和 `dispose()`。

它不得直接调用 `AgentHarness`、Repository、SQLite、文件系统、MCP Transport、Electron IPC 或 Renderer。

### 3.4 AgentEngine、PiAgentEngine 与 AgentHarness

Runtime 只依赖内核端口：

```ts
interface AgentEngine {
  run(
    invocation: AgentInvocation,
    signal: AbortSignal,
  ): AsyncIterable<AgentEvent>
  dispose(): Promise<void>
}
```

`PiAgentEngine` 位于 `src/kernel/pi/**`，实现 `AgentEngine` 并负责：

- 打开当前 Session 对应的 pi Session backend；
- 注入 Model、System Prompt、Tool 和 ToolPolicy；
- 创建并调用 `AgentHarness`；
- 将 `AgentHarnessEvent` 映射为公共 `AgentEvent`；
- 将 Runtime `AbortSignal` 映射为 `AgentHarness.abort()`；
- 验证 canonical message 已持久化后再暴露 `message_end`。

`AgentHarness` 来自 `@earendil-works/pi-agent-core`。它不是独立服务，而是运行在当前进程里的外部库对象，负责模型调用、Tool Call/Result、多 Turn 循环、事件、Session 接入和中止。Runtime、Main、IPC 和 Renderer 都不得直接 import 它。

### 3.5 Persistence 与 Host Port

Runtime 拥有“何时持久化、失败后能否继续、重启后如何恢复”的业务语义，但不拥有具体存储技术：

```text
SessionRepository Port -> SQLite / PostgreSQL
MessageStore Port       -> pi Session backend
ArtifactStore Port      -> Local FS / S3
ExecutionEnv Port       -> Node FS / Sandbox / Worker
MCP Port                -> stdio / HTTP Transport
```

消息只有在 canonical store 持久化成功后才能发出 `message_end`。存储进入 degraded 状态后必须拒绝继续产生副作用。

### 3.6 消息与停止数据流

正常发送：

```text
App.send()
  -> window.tgbuddy.agent.send()
    -> preload ipcRenderer.invoke(agent:send)
      -> Main IPC handler
        -> AgentRuntime.runs.start()
          -> RunCoordinator.start()
            -> AgentEngine.run()
              -> PiAgentEngine
                -> AgentHarness.prompt()
```

事件返回：

```text
AgentHarnessEvent
  -> PiAgentEngine 映射 AgentEvent
    -> RunCoordinator 包装 StreamFrame
      -> AgentRuntime.subscribe()
        -> Main webContents.send(agent:stream)
          -> Preload onStream()
            -> Renderer 全局事件路由
```

主动停止：

```text
UI stop
  -> AgentRuntime.runs.stop(sessionId)
    -> RunCoordinator.stop()
      -> RunRegistry.cancel()
        -> AbortSignal
          -> PiAgentEngine
            -> AgentHarness.abort()
```

停止后 Session 必须收口为 `interrupted`，迟到事件由 Runtime 的 abort guard 和 Renderer 的 `runId` cursor 双重丢弃。

## 4. Composition Root

`src/main/bootstrap/create-application.ts` 是 Electron 宿主唯一 Composition Root，负责创建 SQLite repositories、pi Session backend、`PiAgentEngine` 和 Infrastructure Adapter，再交给临时的 `createLegacyRuntime()` 补齐尚未迁移的 Main compatibility dependencies；该 adapter 最终调用唯一正式工厂 `createAgentRuntime()`。最后才由 `registerIpc(agentRuntime)` 连接 Electron Host Adapter。

服务器版不得复用 Electron `createApplication()`，而应建立同级 Composition Root：

```text
createServerApplication()
  -> create adapters
  -> create PiAgentEngine
  -> createAgentRuntime()
  -> register HTTP / SSE / WebSocket
```

两个宿主复用 `AgentRuntime`、Runtime Port 和 pi/infrastructure factory，不共享 Electron 生命周期代码。

当前 `create-legacy-runtime.ts` 只用于分阶段迁移：

- K01–K17 已删除 Session、orchestrator 与 compaction 委托并切换 SQLite/pi backend。
- S01–S11 删除 permission、plan、question 与全局 sandbox 委托。
- C01–C12 删除 channel 与旧 tool registry 委托。
- U08 删除剩余 IPC/Renderer compatibility owner。
- 它不得新增产品入口，也不能成为第二个长期门面。

R01–R02 只把正式门面、事件和运行命令改为上述语义名称，不伪装或提前删除 compatibility 依赖。S01–C12 继续按 owner 删除期限逐步把剩余依赖移入正式 Port/Adapter。

Electron 退出前调用 `application.dispose()`；IPC handler 不再直接 import store、repository 或 kernel。

## 5. Alias

TypeScript 与 Vite 的同名 alias 必须指向相同目录：

| Alias | Target |
|---|---|
| `@` | `src` |
| `@runtime` | `src/runtime` |
| `@shared` | `src/shared` |

架构 checker 会把同名 alias 的分歧作为违规，避免 TypeScript 能通过但 Vite 解析到另一棵目录。

## 6. 纵向切片迁移

| Milestone | Slice | 主要交付 / 删除的旧 owner |
|---|---|---|
| Baseline | B00–B01 | packaged SQLite 证据、仓库边界与 Runtime 门面，已完成 |
| M1 | K01–K17 | 可恢复 Session/Run/Context；删除 JSONL canonical、裸 orchestrator 和旧 compaction |
| M2 | S01–S11 | Workspace/ExecutionEnv/Policy；删除全局 sandbox 和旧权限 owner |
| M3 | C01–C12 | Channel/Profile/Tool/Skill/MCP；删除 Main 内能力 owner |
| M4 | A01–A09 | Blob、附件、长输出和 Artifact |
| M5 | D01–D04 | 单层 child lineage、预算和取消 |
| M6 | U01–U09 | 原型场景、领域 IPC/Renderer feature、删除 compatibility bridge、7 条 E2E |

兼容层必须同时满足三条：

1. 只委托旧实现，不复制业务规则。
2. 在代码和本文中写明删除 Slice。
3. 新功能不得继续接入兼容层。

## 7. 验证门槛

每个 Slice 至少执行相关单测、`bun run check:architecture`、`bun run typecheck` 和 `bun test`；涉及 Main/Preload/Renderer 或 bundle 时再执行 `bun run build`，kernel/SQLite 变更追加 probe/spike。架构检查与功能测试缺一不可：前者阻止依赖回退，后者证明迁移没有改变行为。
