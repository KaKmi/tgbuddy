# 设计决策

来自交互原型（`tgbuddy-mockup/`）的结论。**这些是已定的**，实现时直接照做，不要重新讨论。

原型有 7 个场景可切换：整窗空状态 / 主窗口 / 工具卡片四态 / 权限确认 / 上下文与压缩 / 会话列表 / 设置。

---

## 决定 1 · 结果区如何组织

**时间倒序 + 类型筛选**（不按类型分组），分「本次任务」和「更早」两段。结果侧栏增加「产物 / 工作区」双入口：产物展示 Agent 输出，工作区展示轻量文件树。预览**只读**，只提供「查看」和「系统打开」；不再提供「让 Agent 改这份」专用按钮，修改需求直接在 Composer 中描述。

**理由**：同一次任务的产物通常一起被查看，按类型分组会把它们拆散。只读避免「用户手改」和「Agent 再写」打架；文件树与独立查看器覆盖定位和阅读，编辑仍交给外部编辑器。结果区保持 356px，避免演化成重型 IDE。

产物条目形如：

```
q2-risk-report.md        刚刚 · write · 14.2 KB      [MD]
exposure-by-account.png  1 分钟前 · chart 技能        [PNG]
clean_trades.py          3 分钟前 · 子智能体改动      [PY]
```

注意第三条——**产物要标注是谁产生的**（主 Agent / 某个技能 / 子智能体）。这个信息从 `ToolDetails` 和 `parentToolCallId` 就能拿到。

## 决定 2 · 工具卡片四态与折叠策略 ★ 实现有讲究

四态：**等待授权 / 执行中 / 成功 / 失败**（另有「已拒绝」）。

**等待授权必须优先于执行中。** 原型给的实现方案比我原来想的更稳：

```js
if (evt === "tool_start")         queue(120ms → running)
if (evt === "permission_request") cancelQueue(); status = "pending"
```

**收到 `tool_start` 后不立刻渲染「执行中」，而是延迟 120ms 入队**；若这期间收到授权请求，取消队列直接落在「等待授权」。

> 实测底层 `tool_start` 比授权请求早约 **5ms**（阶段 1 验证），120ms 是 24 倍余量。
> 这个方案比「查待授权队列」更健壮——不依赖两条信息在同一个 reducer 里同时可见。

**折叠策略**：

| 状态 | 默认 |
|---|---|
| 等待授权 | 展开 |
| 执行中 | 展开尾部输出，完成后自动收起 |
| 成功 | 折成一行 |
| 失败 | 展开，带重试按钮 |

长输出**裁到 8 行**显示，但**完整版仍然送给模型**。子智能体的调用收进一个可折叠组。

## 决定 3 · 「总是允许」的粒度

**组合粒度：工具 × 匹配范围 × 有效期。** 范围随工具类别变。

```ts
interface PermissionRule {
  tool: string                                    // "bash" | "read" | "postgres.query"
  match: 'tool' | 'path' | 'prefix' | 'method'
  pattern: string                                 // "~/project/**" | "git status"
  scope: 'session' | 'project' | 'global'         // 默认 project
  neverPersist: boolean                           // rm/sudo/重定向 命中即 true
}
```

| 工具类别 | 匹配方式 | 例子 |
|---|---|---|
| 文件类 | 路径 glob | `~/project/tmp/**` |
| 命令类 | 命令前缀 | `git status` |
| 连接器 | 服务.方法 | `postgres-read · select` |

**理由**：单一粒度必错——按工具太粗（一次点击等于交出 shell），按参数太细（每个新文件都要重问）。

**破坏性命令不可持久化**，黑名单：`rm` / `sudo` / `chmod 777` / `> /` / `curl … | sh` / `git push --force`。命中即 `neverPersist: true`，只能一次一次批。这类操作的价值恰恰在于每次都停一下。

**默认有效期是「本项目」**，换工作区自动失效。

### inline 还是模态

**inline 为默认**，「高危 + 不可逆」升级为模态。inline 卡片配一条**底部常驻的「1 个授权请求等待处理」跳转条**，解决被划过去的问题。

用**危险等级**而不是工具名做升级判据——规则简单且可解释。

## 决定 4 · 压缩自动还是手动

**自动，85% 阈值**，手动可提前触发。

- 触发前给 **3 秒「稍后」窗口**——不在关键一步前动上下文
- 进行中在对话流插一条**带进度的占位**，**输入框不锁死**，消息排队发送
- 完成后留一条**可展开的分隔线**，原始消息仍在本地库

**理由**：压缩要调一次模型、有几秒延迟，让用户确认等于在任务中途打断他。被压缩的消息彻底消失会让用户怀疑数据丢了。

## 决定 5 · 会话不做分支 / 时间旅行 ★ 直接简化存储

**不需要。存储保持一条 append-only 线性日志，不建树。**

三条理由：

1. Agent 任务是目标导向的，用户要「重来一次」而不是「保留两条路对比」
2. 树形历史的成本全在 UI 与心智模型上——一旦有分支就要有分支切换器、diff、合并语义，而用户真正用到的只有「回到那一步」
3. 替代方案更便宜

替代方案：

```ts
Session  { id, messages: Message[] }              // 线性
Message  { id, truncatedAt?, supersededBy? }
Session.originRef?: { sessionId, messageId }      // 扁平引用，非树
```

- **编辑并重发** = 截断后面的消息（**软删除、可撤销**）
- **以此为起点新建会话** = 把上下文摘要复制进新会话，两个会话之间只记一个 `originRef` 指针

> 这条推翻了原架构里「用 pi 的 `id`/`parentId` 会话树」的设计。[01-架构设计.md](01-架构设计.md) 4.1 已同步修订。

## 决定 2.5 · 系统标记的统一语言

对话流里的系统插入标记（切换专家、压缩、重试）用统一样式。权限模式由输入框上方的 Chip 持续展示，不重复写进对话流：

**一行 12px 次要色 + 18px 圆角字形徽标 + 向右淡出的细线。**

| 类型 | 可否展开 |
|---|---|
| 有细节的（压缩、切换专家） | 可展开 |
| 纯事实的（重试） | 不可展开 |

**理由**：标记不是对话内容，所以不用气泡、不占对话缩进；但要能被扫到，所以用一条贯穿的淡线和消息区分开。用**字形而不是彩色图标**，避免和工具卡片的状态色抢注意力。

## 决定 6 · 空状态

**空状态不是边缘情况。**

- **整窗空状态**：给三个可点的任务样例 + 当前模式
- **结果区空状态**：解释「左边是过程、右边是结果」

用户看空状态的次数比看任何具体产物都多。

## 决定 7 · 设置按应用级能力收口

| 页 | 内容 |
|---|---|
| **通用** | 启动恢复、新会话默认模式、本地数据与脱敏诊断；Session 标题自动生成是固定行为，不提供设置项 |
| **模型** | 主 Agent、子智能体、压缩摘要的模型分工；Provider、连通性与本机钥匙串 |
| **工具与权限** | 权限模式、真实「总是允许」规则、只读工具分类默认；不提供 per-tool 三档 |
| **能力** | 应用级 Skill 与 MCP 管理、状态、开关/连接、工具发现与错误恢复 |
| **外观** | 明亮/深色主题与显示偏好 |

Skill 与 MCP 不再做工作区级启用配置，也不占 Composer 的主路径。它们由应用统一管理，每次 Run 仍按 Profile、权限和当前可用状态固化能力快照。工作区内发现的 Skill 可以标注来源，但不产生第二套工作区配置 owner。

## 附带确认的其它设计

**三栏配色**：会话栏 `#0e0e0f` 比对话区 `#141415` **深一档**拉层次，不靠边框——和 [05-design.md](05-design.md) 里那条 `--background` / `--content-area` 双背景的做法一致。

**工作区是一等概念**。原型里侧边栏顶部是工作区切换器，每个工作区带路径和会话数：

```
交易风控   ~/work/risk-q2      6 会话
合同比对   ~/work/contracts    2 会话
临时草稿   ~/Desktop/scratch   空
```

会话、产物、Mount 和授权规则按工作区隔离；Skill/MCP 的启用与连接配置属于应用级，不随工作区切换。

**输入框上方只保留两个主要入口**：模式 / 专家，右侧是模型与上下文。Skill/MCP 不显示为工作区 chip；Agent 在 Run 启动时从应用级能力中按需加载。每个菜单项带一句说明，比如权限模式：

- 默认权限 —— 只读工具直接执行，写和命令逐次授权
- 计划模式 —— 先出计划，你批准后才动手
- 完全访问 —— 不再询问。仅建议在沙箱或一次性容器里用

## 决定 8 · Agent Runtime 是唯一应用运行时边界

**Electron、Web Server 和未来 CLI 都只能通过 `AgentRuntime` 调用 Agent 应用能力。** `AgentRuntime` 是产品与部署层面的统一名称；代码内部继续保留 Runtime 业务核心、pi 内核适配和 Infrastructure Adapter 三层，不能为了“看起来统一”把具体实现塞回 Runtime。

```text
Desktop / Web / CLI
  -> Host Adapter（Electron IPC / HTTP + SSE）
    -> AgentRuntime
      -> RunCoordinator
        -> AgentEngine Port
          -> PiAgentEngine
            -> AgentHarness（@earendil-works/pi-agent-core）
```

### 已定命名

| 语义 | 名称 | 说明 |
|---|---|---|
| 应用运行时门面 | `AgentRuntime` | 宿主唯一调用入口 |
| 构造门面 | `createAgentRuntime(dependencies)` | 只组合显式依赖，不创建 Electron、数据库或文件系统实例 |
| 门面依赖 | `AgentRuntimeDependencies` | Runtime 所需命令、查询和端口集合 |
| 启动一次 Run | `runtime.runs.start(input)` | “启动运行”，区别于前端“发送消息” |
| 运行调度 | `RunCoordinator.start(input, emit)` | 管理 Run 生命周期，不执行模型循环 |
| 内核端口 | `AgentEngine.run(invocation, signal)` | Runtime 对具体 Agent 内核的唯一依赖 |
| pi 端口实现 | `PiAgentEngine` | 把 Runtime invocation/event 映射到 pi |
| pi 底层执行器 | `AgentHarness` | 外部依赖，执行模型、Tool 与多 Turn 循环 |

前端 API 保留 `window.tgbuddy.agent.send(input)`，因为它表达的是用户动作；Main IPC 收到消息后必须立即翻译为 `runtime.runs.start(input)`。不能让 IPC 直接调用 `RunCoordinator`、`PiAgentEngine`、`AgentHarness`、Repository 或 Store。

### RunCoordinator 的边界

`RunCoordinator` 只负责一次 Run 从启动到收尾的业务编排：

- 同一 Session 只允许一个 root Run，不同 Session 可以并行；
- 分配 `runId` 与 `AbortSignal`，处理停止和迟到事件；
- 调用 invocation factory 获得本次 Run 的不可变快照；
- 调用 `AgentEngine.run()` 并把内核事件包装为 `StreamFrame`；
- 推进 Session 的 `running -> done | failed | interrupted` 生命周期；
- 观察 Context usage，确保异常、中止和 `dispose()` 都完成收尾。

它不负责模型循环、Tool 实现、SQLite、文件系统、MCP transport、Electron IPC 或 UI。

### 持久化边界

Session、Message、Run、Workspace 和 Artifact 的**领域语义与持久化时机**属于 Agent Runtime；SQLite、PostgreSQL、Blob、文件系统等**具体实现**属于 Infrastructure。Runtime 只依赖 Repository/Store Port。

```text
AgentRuntime -> SessionRepository Port -> SQLite / PostgreSQL
AgentRuntime -> MessageStore Port       -> pi Session backend
AgentRuntime -> ArtifactStore Port      -> Local FS / S3
AgentRuntime -> ExecutionEnv Port       -> Node FS / Sandbox / Worker
```

消息必须先由 canonical store 持久化成功，才能向宿主暴露 `message_end`。存储进入 degraded 状态时必须阻止后续副作用，不能只记录日志后继续运行。

## 决定 9 · Session 标题由 LLM 异步生成

新会话发送首条用户消息后，先显示“正在生成标题…”；root Run 完成 Provider/模型解析后，使用同一渠道与选中模型发起一次短标题请求。标题生成不阻塞主 Run，成功后实时更新 Sidebar 与 Header，失败则保留首条用户消息的安全截断标题。

写回必须使用来源守卫：Session 标题区分 `default / generated / user`。只有仍为 `default` 时生成结果才能写回；用户手动重命名立即标记为 `user`，任何迟到的生成结果都不得覆盖。重启后沿用已持久化标题，不重复生成。

参考 Prom 的“默认标题守卫 + 后台生成 + title updated 通知”流程，但 TgBuddy 的 Provider 调用必须进入 `src/kernel/pi/**`，业务竞争与写回规则属于 Runtime，Main IPC 只转发事件。

### 部署边界

广义的“TgBuddy Agent Runtime”部署单元包括：

```text
Runtime 业务核心
+ PiAgentEngine
+ AgentHarness
+ Infrastructure Adapters
```

狭义的 `src/runtime/**` 只包含业务语义、用例、状态机和 Port，不得依赖 pi、Electron、Node 文件系统、SQLite 或具体 Infrastructure。这样 Electron 与 Web Server 可以复用同一套 Agent Runtime，只替换 Host Adapter 和部署环境 Adapter。
