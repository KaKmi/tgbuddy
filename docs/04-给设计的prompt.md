我在做一个叫 **TgBuddy** 的 AI Agent 桌面应用（Electron + React，中文界面，本地优先，数据不出本机）。请帮我设计交互原型。

## 产品是什么

一个能自主执行任务的 AI Agent 客户端。用户下达任务，Agent 自己调用工具（读写文件、执行命令、搜索、调用 MCP 服务）来完成，遇到危险操作时向用户请求授权。类似 Claude Code / Cursor 的 Agent 模式，但是图形界面。

**没有普通聊天模式**，只有 Agent 模式。

## 整体布局（已定，请沿用）

三栏：**侧边栏（会话列表） · 对话区 · 结果区**

第三栏是「结果区」而不是文件树。原因：对话区展示的是**过程**，用户真正要的是**产物**。一次任务可能有几十次工具调用滚过去，最后生成的那份报告、那张图、那个改好的文件会被埋在工具噪音里。结果区专门收纳「本次会话的产出」。

输入框上方有一排入口：**模式 · 专家 · 技能 · 连接器**，右侧是模型选择和上下文用量百分比。

- **模式** = 权限模式（默认权限 / 计划模式 / 完全访问）
- **专家** = 预设的角色人格，可单个使用也可组成团队（如"交易分析团队"）
- **技能** = 可按需加载的能力包
- **连接器** = MCP 服务

## 请设计这五个屏幕

### 1. 主窗口

三栏布局的整体样子。需要明确：

- 结果区的产物如何组织（时间顺序？按类型分组？）
- 预览支持哪些类型（markdown 渲染 / 代码高亮 / 图片 / HTML）
- 产物是只读预览还是可编辑
- **结果区的空状态** —— 每个会话开始时它都是空的，这个状态用户看到的次数比任何具体产物都多，请认真设计，不要当边缘情况
- 整窗空状态（一个会话都没有时）

### 2. 工具活动卡片 ★ 最重要

一次工具调用在对话流里的呈现。这是整个应用信息密度最高、也最容易做砸的地方。

**硬约束：卡片必须有四种状态，且「等待授权」要优先于「执行中」显示。**

技术原因：底层框架发出"开始执行工具"的事件比弹出授权请求早约 5 毫秒。如果卡片直接按"执行中"渲染，用户会先看到「正在执行 rm -rf ...」、然后才弹出授权框——看起来像是没经过同意就动手了，信任感会崩。

四态：**等待授权 / 执行中 / 成功 / 失败**

还需要解决：

- 默认折叠还是展开？（一次任务可能有几十次工具调用，全展开会淹没对话）
- 结构化参数怎么显示？原始 JSON 还是人话摘要（"读取 config.ts"）
- 长输出怎么处理？（比如搜索返回 200 行）
- 子 Agent 派发的任务，其内部的工具调用如何收进一个可折叠的组

### 2.5 对话流里的系统级标记

除了消息和工具卡片，对话流里还会出现几种**系统插入的标记**，需要一套统一的视觉语言（比消息弱、但能被看见）：

- **切换专家**：「已切换到『合同法务专家』，可用能力已更新」
- **上下文压缩**：「已压缩 N 条历史消息」（可展开查看）
- **重试**：「第 2 次重试（网络错误）」

请设计这类标记的统一样式。它们不是对话内容，但用户需要知道发生了什么。

### 3. 权限确认 ★ 需要你帮我做决定

Agent 要执行危险操作时的授权界面。

**核心问题：「总是允许」的粒度应该是什么？** 这个决定会写死在数据结构里，请给出建议：

- 按工具（允许后 `read` 全部放行）
- 按路径（`~/project/**` 下的读写都放行）
- 按命令前缀（`git status` 放行，但 `git push` 仍要问）
- 组合

粒度太粗不安全，太细用户会被问烦。

还需要解决：

- inline 卡片还是模态弹窗？（inline 不打断阅读但容易被划过去；模态强制响应但打断心流）
- 需要展示什么信息？工具名、完整参数、将影响哪些文件、危险等级
- 拒绝之后要不要让用户填一句理由给 Agent（让它换个方式做）
- 多个请求接连到来时怎么呈现（不会同时来一堆，但会一个接一个）

### 4. 上下文用量与压缩

一个显示上下文占用的面板，分类展示：

```
43.1%  已使用 72.5K / 168.0K
  系统提示词      ~9.7K
  工具及子智能体   ~25.3K
  对话消息        ~36.1K
  连接器及 MCP     ~103
  技能            ~1.2K
```

当上下文快满时会触发「压缩」——把旧消息总结成摘要腾出空间。需要设计：

- 压缩是自动发生还是需要用户确认？
- 压缩进行中对话区显示什么？（需要调一次大模型生成摘要，有几秒延迟）
- 被压缩掉的历史消息在界面上怎么呈现？彻底消失？还是留一条可展开的「已压缩 N 条消息」分隔线？

### 5. 会话列表 ★ 需要你帮我做决定

**核心问题：会话需要分支 / 时间旅行吗？**

如果需要，用户可以「从这条消息重新开始」，或者 fork 一个会话去试另一条路，历史形成一棵树而不是一条线。

请从产品价值角度判断这个功能值不值得，并给出对应的界面呈现。**如果判断不需要，请明确说不需要**——我会据此简化底层的存储结构。

其余：置顶、归档、按日期分组、搜索、正在流式输出的会话如何标示。

## 视觉方向

现代、克制。用卡片和阴影取代边框，饱满但不刺眼的主色。中文界面，字体层级要清晰。整体气质接近 Linear / Raycast，不要企业级后台的那种密集感。

## 不需要设计

设置页各 tab、专家和团队的管理界面、附件上传、主题切换。这些要么已有参考，要么排期很靠后。

## 加分项（有余力再做）

**技能与工具的设置页。** 这一页有个特殊需求，没有现成参考：

技能和工具的 schema 都常驻在模型的上下文里，能力开得越多，可用的对话空间越少。所以这个设置页不只是开关列表，**每个分组要显示它当前占用多少上下文**：

```
工具
  内置 (6)                    ~12.4K tokens   [全部启用 ▾]
    ☑ read      读取文件           ~1.2K
    ☑ bash      执行命令           ~3.1K
    ...
  连接器提供 (3)               ~8.0K
技能
  内置 (5)                     ~0.6K          [检查更新]
  工作区 (13)                  ~1.6K          [+ 添加]
```

目标是让「关掉不用的能力」变成一个**有依据的决策**，而不是凭感觉点开关。请设计这个信息如何呈现才不显得技术味太重。
